## 1. Purpose

Educational CUDA implementation of exact scaled-dot-product attention (forward pass only),
progressing from a naive multi-kernel baseline to a tiled, IO-aware FlashAttention-style kernel.
Full roadmap: [`MILESTONES.md`](MILESTONES.md). Original planning: [`flash-attention-project.md`](flash-attention-project.md).

## 2. Target hardware

**Execution model.** Hybrid: local Mac (Apple Silicon, no CUDA) for editing / CPU reference / plotting; Colab T4 (`sm_75`, free) for dev iteration and correctness checks; Modal A10G (`sm_86`, ~$1.10/hr) for deliverable-quality benchmarks and Nsight profiling in M9/M10.

## 4. Repository layout

```text
csrc/               C++/CUDA kernels. One file per variant.
tests/              pytest suite. Correctness against CPU/PyTorch oracle.
benchmarks/         Sweep script + result CSVs + plot script.
benchmarks/results/ Committed CSVs and .ncu-rep files.
scripts/            build.sh / test.sh / bench.sh / profile_ncu.sh / reproduce.sh
docs/               MILESTONES.md, AGENTS.md, focused writeups, plots/
docs/plots/         PNGs generated by benchmarks/plot.py and benchmarks/roofline.py
notebooks/          demo.ipynb (M10). Recruiter-facing 30-second demo.
```

Why no `include/`? — kernels are private to `csrc/` for now; there is no external C++ API.
Why no `bindings/`? — the pybind11 shim lives in `csrc/` beside the kernels it wraps (added in M4/M5).

## 5. Conventions

### 5.1 Tensor layout

Row-major `[B, H, N, D]`:

- `B` — batch.
- `H` — heads.
- `N` — sequence length.
- `D` — head dim.

Why not `[B, N, H, D]`? — We want threads within a warp to hit contiguous elements along `D` (the fastest-varying axis inside a head), and heads to be independent CTA-grid work. `[B, H, N, D]` gives coalesced loads for `Q[b, h, i, :]` and independent CTAs per `(b, h)`.

### 5.2 Kernel naming

`csrc/<family>_<variant>.cu`. Examples:

- `attention_naive.cu` — naive multi-kernel baseline (M2).
- `attention_online_ref.cu` — online-softmax reference (M3).
- `flash_fwd_v1.cu` — first tiled forward (M4).
- `flash_fwd_v2_shared_kv.cu` — better shared-mem layout (M6).
- `flash_fwd_v3_causal.cu` — causal / batch / multi-head (M7).

### 5.3 Commit conventions

Conventional Commits: `feat:` `fix:` `refactor:` `test:` `perf:` `docs:` `bench:` `chore:`.
Scope in parens when useful, e.g. `feat(flash-v1): tiled forward for D=32,64`.

**No `Co-authored-by:` trailers and no tool/agent attribution in commit messages.** Authorship stays clean and human.

### Running on Colab T4 (quickstart)

Every Colab session starts fresh. Clone the repo first, then use `scripts/bootstrap_colab.sh` — it auto-detects the GPU's compute capability, pulls the latest `main`, installs Python deps, builds, and runs the smoke test.

**First cell of a fresh Colab session:**

```bash
!git clone https://github.com/<user>/<repo>.git
%cd flash-attention-from-scratch
!bash scripts/bootstrap_colab.sh
```

**After every `git push` from local — resync + rebuild:**

```bash
!bash scripts/bootstrap_colab.sh
```

**Fast re-run when only kernel/build changed** (skip `pip install`):

```bash
!SKIP_PIP=1 bash scripts/bootstrap_colab.sh
```

Timings on Colab T4: first run ≈ 2-3 min (pip + build), subsequent runs ≈ 10-15 s with `SKIP_PIP=1`.

After the very first run in a fresh session, paste the `./build/hello` output into §2 (T4 row) and commit.

## 7. How to add a new variant

1. Create `csrc/<family>_<variant>.cu`.
2. Add it to `CMakeLists.txt` (extend the existing target or add a new one).
3. Expose a launch wrapper — pure host function `void <name>_forward(Q, K, V, O, …)`.
4. Register the variant in the pytest parametrization (`tests/test_all_variants.py`, added in M5).
5. Register the variant in `benchmarks/bench_attention.py` (added in M5).
6. Add a row to the variant table in [`../README.md`](../README.md).
7. Commit as `feat(<variant>): <one-line description>`.

## 8. Open decisions

Resolved during M0:

- [x] **Target arch.** Default `sm_86` (Modal A10G is the reference GPU). Override to `75` for Colab T4 via env var.
- [x] **GPU access.** Hybrid: Colab T4 free tier for dev, Modal A10G ($30 credits) for deliverable-quality runs, Mac local for CPU/docs.
- [x] **Toolchain on Colab.** CUDA 12.8.93, Python 3.12.13, PyTorch 2.11.0+cu128. Modal side to be added when M5's Modal setup lands.

Resolved during M1:

- [x] **Python binding style.** `pybind11` shim (lands in M4). Industry standard; matches the official `flash-attn` repo; portable to non-torch consumers. Rejected: `torch.utils.cpp_extension` (simpler but torch-locked).
- [x] **Test framework for pure-C++/CUDA paths.** GoogleTest for pure-C++ host code (starting with `attention_cpu_ref.hpp` in M1); pytest via pybind11 for CUDA kernels from M4. Matches CUTLASS/PyTorch practice — test each layer in its native framework, ~1 s C++ test round-trip.

Resolved during M3:

- [x] **M3 online-softmax kernel test surface.** GoogleTest only in M3 (the `test_attention_online_ref` binary covers the full verification grid + edge cases). Python parity (`tests/test_online_softmax.py`) waits for the M5 harness once pybind11 lands in M4 — same tradeoff M2 accepted. Kernel is exercised end-to-end from C++, so nothing is untested; the deferral only affects the reporting surface.

## 9. Numerical tolerance policy

Set in M1, pinned in each milestone's verification:

| Regime | Abs tol | Rel tol | Compared against |
|---|---|---|---|
| CPU ref vs PyTorch, fp32 | `1e-5` | — | `torch.nn.functional.scaled_dot_product_attention` |
| CUDA kernels, fp32 | `5e-4` | — | CPU ref |
| M3 online-softmax vs CPU ref, fp32 | `1e-5` | — | CPU ref — algebraic equivalence, not matmul-accumulation drift |
| CUDA kernels, fp16 in / fp32 accum | `5e-3` | `1e-2` | CPU ref (fp32) |

## 10. Anti-scope (short form — full version in [`MILESTONES.md`](MILESTONES.md))

- No backward pass.
- No dropout, packed varlen, or paged attention.
- No tensor-core / WMMA path in v1.0.0 — the gap to `flash-attn` is the thing we *analyze*.
- No Hopper-only features (TMA, WGMMA, FP8).
