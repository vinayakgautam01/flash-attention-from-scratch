## 1. The one-sentence goal of M6

> **Make the exact same algorithm run several times faster by changing only where operands live and how many hardware cycles it costs to fetch them.**

Not one line of the online-softmax recurrence from [`M3.md`](M3.md) changes. Not one tile shape changes. The output must match v1 to round-off. M6 is the milestone where you demonstrate that you can profile, form a hypothesis, change one thing, and prove the metric moved.

The thesis in one line:

> **v1 isn't slow because it does too much work. It's slow because it spends ~98% of its time waiting.**

Everything below identifies the two things it waits for and removes them.

## 2. What M6 is *not* (especially: not FlashAttention-2)

**This is not FlashAttention-2 the paper.** That matters enough to say twice, because "v2" is an overloaded name and a reviewer who sees `flash_fwd_v2` will assume the paper unless we say otherwise.

| | FlashAttention-2 (Dao, 2023) | our Flash v2 (M6) |
|---|---|---|
| Loop order | outer = KV-tile | outer = Q-tile (unchanged from FA-1) |
| Work partitioning | sequence-parallel across CTAs | none (unchanged) |
| Cross-CTA state merge | yes (the `(m, ℓ, Õ)` monoid combine) | no |
| Non-matmul FLOP reduction | yes (rescale hoisted out of the loop) | no |
| What actually changes | the algorithm | only the mechanics |

The real FA-2 loop reversal stays out of scope for `v1.0.0` and is named in M10's "reading the gap" section — see [`../docs/flash_attention_notes.md`](../docs/flash_attention_notes.md) §6.

Also out of scope for M6:

- **Not tensor cores / WMMA.** Explicit anti-scope per [`../docs/AGENTS.md`](../docs/AGENTS.md) §10.
- **Not `cp.async`.** Turing (Colab T4, our dev GPU) doesn't have it. Ampere-gated path is M7 at the earliest.
- **Not `D = 128`.** Needs the 64 KB smem opt-in; M7.
- **Not batch / multi-head / causal *testing*.** The kernel supports all three (grid carries `B*H`, the mask is implemented, and there is a causal smoke test), but the formal grids are M7.
- **Not fp16.** M8.
- **Not new math.** If you find yourself changing the recurrence, you've left M6.

## 3. Diagnosis: where is v1's time actually going?

You cannot optimize what you haven't measured. Take the canonical row from [`../benchmarks/results/all.csv`](../benchmarks/results/all.csv) at `N = 2048, D = 64, B = H = 1` on Colab T4:

```
flash_fwd_v1,1,1,2048,64,False,fp32,11.647520,...,68157440,...,0.0922,...
```

### 3.1 Three numbers that should not coexist

**Total useful FLOPs.** Two matmuls, each \(2N^2D\):

\[
\text{FLOP} = 4N^2D = 4 \cdot 2048^2 \cdot 64 = 1.074 \times 10^9
\]

**If it were compute-bound.** T4 peak fp32 is 8.1 TFLOP/s (`AGENTS.md` §2.1):

\[
t_{\text{compute}} = \frac{1.074 \times 10^9}{8.1 \times 10^{12}} = 0.133\ \text{ms}
\]

**If it were bandwidth-bound.** 68.16 MB at T4's 320.1 GB/s:

\[
t_{\text{HBM}} = \frac{68.16 \times 10^6}{320.1 \times 10^9} = 0.213\ \text{ms}
\]

**Measured: 11.65 ms.** That is 55× the larger of the two predictions.

```
   math:          ▏                                          0.13 ms   (1.1% of peak)
   data movement: ▎                                          0.21 ms   (1.8% of peak BW)
                  └──────────────────────────────────────┘
   MEASURED:      ███████████████████████████████████████   11.65 ms
```

### 3.2 The roofline reading (preview of M9)

\[
\text{AI}_{\text{v1}} = \frac{1.074\times 10^9\ \text{FLOP}}{68.16 \times 10^6\ \text{B}} = 15.75\ \text{FLOP/B},
\qquad
\text{AI}_{\text{ridge}}^{\text{T4}} = \frac{8.1\times10^{12}}{320.1\times10^9} = 25.3\ \text{FLOP/B}
\]

v1 sits left of the ridge, so its ceiling is the memory roof at \(15.75 \times 320.1 = 5.04\) TFLOP/s. It delivers 0.0922. **v1 is at 1.8% of its own roofline ceiling.** It is not on any roof — which by definition means it is bound by something the roofline model does not draw: **on-chip throughput and latency.**

This kills the natural misconception. "Attention is memory-bound" is true of the *naive* kernel; it is not true of ours. v1 has already fixed the DRAM problem — and then created a new one on-chip.

### 3.3 It's a per-CTA problem, not a scheduling one

From the CSV at `D = 64`, `tflops_effective` reads 0.0335, 0.0842, 0.0909, 0.0922 for `N = 256, 512, 1024, 2048`. It **saturates at ~0.09 and stops improving** once the GPU is full (at `N = 2048` we launch \(T_r = 64\) CTAs on 40 SMs).

If the problem were under-utilization, throughput would keep climbing with `N`. It doesn't. **Whatever is wrong is wrong inside a single CTA.** (The genuinely separate small-`N` under-utilization story is in `flash_attention_notes.md`; it is a launch-config problem no amount of M6 work fixes.)

### 3.4 Two candidates

On a Turing SM, only two things can burn time that is neither math nor DRAM:

1. **Queueing for shared memory** — bank conflicts. §4–§5.
2. **Stalling with nothing else to run** — one CTA per SM. §7.

v1 has both.

## 4. Background: how shared memory really works

Skip this section if `gcd(stride, 32)` already means something to you.

### 4.1 Banks

A warp is 32 threads executing one instruction at the same instant. When that instruction is a shared-memory load, 32 addresses arrive simultaneously. Serving them one at a time would take 32 cycles, so shared memory is built as **32 independent banks**, each able to serve one address per cycle. Which bank a float lands in is fixed:

\[
\text{bank}(a) = a \bmod 32, \qquad a = \text{index in floats (not bytes)}
\]

The instruction is serviced in **wavefronts**:

\[
W = \max_{k \in [0,32)} \big|\{\text{distinct addresses requested by lanes mapping to bank } k\}\big|
\]

with one special case: if **all 32 lanes request the same address**, the hardware **broadcasts** it in a single wavefront, free.

### 4.2 The picture

Draw shared memory as a grid 32 floats wide. **The column you land in is your bank.**

```
             ←──────────── 32 banks ────────────→
       col:    0     1     2     3    ...   30    31
            ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
            │  0  │  1  │  2  │  3  │ ... │ 30  │ 31  │
            │ 32  │ 33  │ 34  │ 35  │ ... │ 62  │ 63  │
            │ 64  │ 65  │ 66  │ 67  │ ... │ 94  │ 95  │
            └─────┴─────┴─────┴─────┴─────┴─────┴─────┘

     GOOD — lanes spread sideways        BAD — lanes stacked up
     ┌───┬───┬───┬───┬───┐               ┌───┬───┬───┬───┐
     │L0 │L1 │L2 │L3 │L4 │               │L0 │   │   │   │
     └───┴───┴───┴───┴───┘               │L1 │   │   │   │
          W = 1  ✔                       │L2 │   │   │   │
                                         │L3 │   │   │   │
                                         └───┴───┴───┴───┘
                                             W = 32  ✘
```

**Horizontal = fast. Vertical = disaster. Same cell = free.**

### 4.3 The lane-stride theorem

Nearly every shared access in our kernel has the form \(a(\text{lane}) = c + s\cdot\text{lane}\). The set \(\{s t \bmod 32 : t \in [0,32)\}\) is the subgroup of \(\mathbb{Z}_{32}\) generated by \(s\), i.e. the multiples of \(g = \gcd(s,32)\), which has \(32/g\) elements. By pigeonhole each is hit by exactly \(g\) lanes, and for \(s \neq 0\) all 32 addresses are distinct. Hence:

\[
\boxed{\,W = \gcd(s,\ 32)\,}
\]

| stride \(s\) | \(W\) | shape |
|---|---|---|
| 1 | 1 | horizontal ✔ |
| 2 | 2 | 2 stacked |
| 32, 64, 96 | 32 | vertical ✘ |
| any **odd** \(s\) | 1 | diagonal ✔ |

**Corollary that drives the whole fix: a lane-stride is conflict-free iff it is odd.** Padding a row-major tile's leading dimension from \(D\) to \(D+1\) makes the stride odd for even \(D\). It is not a heuristic; it is \(\gcd(D+1,32)=1\).

### 4.4 How to read any line of the kernel

`block = (Bc=32, Br=32)` in v1, so `tid = ty*32 + tx` and warp id `= ty`. **One warp owns one Q row, with `tx` running 0..31 as the lane.** Therefore:

> **`tx` is the lane. `ty`, `d`, `c`, `k` are constants, identical across all 32 lanes at that instant. Find how far the index moves when `tx` increments — that's the stride.**

## 5. Change 1 — the padded `sK` stride

### 5.1 Auditing every shared access in v1

| Step | Access | Lane-varying term | Stride \(s\) | \(W = \gcd(s,32)\) |
|---|---|---|---|---|
| 1 | `sK[ty*D + d]` store, `d = tx + k·Bc` | `tx` (coeff 1) | 1 | 1 ✔ |
| 1 | `sV[ty*D + d]` store | `tx` (coeff 1) | 1 | 1 ✔ |
| 2 | `sQ[ty*D + d]` | *none* | — | broadcast ✔ |
| 2 | **`sK[tx*D + d]`** | `tx` (coeff `D`) | **64** | **32** ✘ |
| 4 | `sm[ty]` | *none* | — | broadcast ✔ |
| 5 | `sS[ty*Bc + tx]` store | `tx` (coeff 1) | 1 | 1 ✔ |
| 7 | `sS[ty*Bc + c]` | *none* (`c` is the loop counter) | — | broadcast ✔ |
| 7 | `sV[c*D + d]`, `d = tx + k·Bc` | `tx` (coeff 1) | 1 | 1 ✔ |
| 7 | `sO[ty*D + d]` | `tx` (coeff 1) | 1 | 1 ✔ |

**Exactly one line is conflicted.**

### 5.2 Correction to the M4 backlog

[`../docs/flash_attention_notes.md`](../docs/flash_attention_notes.md) §2 claimed `sV` had the same 32-way conflict in STEP 7. It does not, and the error is instructive: it reads `c` (the **inner loop counter**, uniform across lanes) as the lane-varying term, when in fact `d = tx + k·Bc` carries the lane, giving stride 1.

Consequence for the plan: M6 is a **one-array, one-integer** change, not the three-buffer layout redesign the notes implied. That file has been corrected as part of this milestone.

### 5.3 Why the conflicted line is conflicted

`sK` is `[32][64]` row-major, so each row is exactly two grid-rows long and **every row starts back at column 0**. Thread `tx` reads row `tx` at a fixed column `d` — i.e. the warp reads a **column** of the table:

```
   sK, row length 64 (2 full bank-rows)     the warp reading column d:

        bank:  0    1    2   ...  31
             ┌────┬────┬────┬────┬────┐     bank 0 does all the work;
  sK row 0 → │ L0 │    │    │    │    │     banks 1..31 idle
             │    │    │    │    │    │
  sK row 1 → │ L1 │    │    │    │    │
             │    │    │    │    │    │
  sK row 2 → │ L2 │    │    │    │    │
                  ⋮  (32 lanes deep)
```

In one sentence: **we read a column of a row-major matrix whose row length is a multiple of 32, so all rows line up and a column is a vertical line.**

It is not avoidable at the algorithm level: the dot product \(Q_i \cdot K_j\) requires lane `tx` to walk down `K` row `tx`, so the 32 lanes are inherently on 32 different rows at the same column. The *layout* is what's wrong.

### 5.4 How much it costs

Per warp, per KV-tile, at `D = 64`:

| Access | Instructions | \(W\) | Wavefronts |
|---|---|---|---|
| STEP 1 `sK`/`sV` stores | 4 | 1 | 4 |
| STEP 2 `sQ` | 64 | 1 | 64 |
| **STEP 2 `sK`** | **64** | **32** | **2048** |
| STEP 4/5/6 scalars | 4 | 1 | 4 |
| STEP 7 `sS` | 64 | 1 | 64 |
| STEP 7 `sV` | 64 | 1 | 64 |
| STEP 7 `sO` | 4 | 1 | 4 |
| **Total** | | | **2252** |

\[
\frac{2048}{2252} = \mathbf{90.9\%\ of\ all\ shared\text{-}memory\ traffic\ is\ one\ line.}
\]

Order-of-magnitude time check. T4 shared memory delivers 32 banks × 4 B = 128 B/cycle/SM, so one conflict-free warp-wide `LDS` retires in ~1 cycle:

\[
64\ \text{CTAs} \times 32\ \text{warps} \times 64\ \text{tiles} \times 2252 = 2.95 \times 10^8\ \text{wavefronts}
\]
\[
t_{\text{smem}} \approx \frac{2.95\times10^8}{40 \times 1.59\times10^9} \approx 4.6\ \text{ms}
\]

Against a measured 11.65 ms, this crude model accounts for ~40% — and it's a lower bound (it ignores issue slots, barrier waits, and exposed LDG latency). Compare with §3.1's 0.133 ms of compute and 0.213 ms of DRAM: **shared memory outweighs both by 20–35×.**

### 5.5 The fix

Store `sK` as `[Bc][D+1]`. The STEP-2 lane-stride becomes \(D+1\), and \(\gcd(65,32)=\gcd(33,32)=1\):

```
     BEFORE (row length 64)              AFTER (row length 65)
     shelf: 0   1   2   3                shelf: 0   1   2   3
          ┌───┬───┬───┬───┐                   ┌───┬───┬───┬───┐
   row 0→ │L0 │   │   │   │            row 0→ │L0 │   │   │   │
   row 1→ │L1 │   │   │   │            row 1→ │   │L1 │   │   │
   row 2→ │L2 │   │   │   │            row 2→ │   │   │L2 │   │
   row 3→ │L3 │   │   │   │            row 3→ │   │   │   │L3 │
          └───┴───┴───┴───┘                   └───┴───┴───┴───┘
        VERTICAL — 32 cycles                DIAGONAL — 1 cycle
```

**Cost: \(B_c \times 1 \times 4 = 128\) bytes.** Post-fix wavefronts per warp per tile: \(2252 - 2048 + 64 = 268\), an **8.4× reduction**.

Check the write side doesn't regress: STEP 1 stores `sK[ty*(D+1) + d]` with `d = tx + k·Bc`; lane-stride is still 1. ✔

### 5.6 Two alternatives, and why padding wins

**Transpose to `sKT[D][Bc].** STEP 2 reads `sKT[d*Bc + tx]`, stride 1, conflict-free. But STEP 1 then stores `sKT[d*Bc + ty]` with `d = tx + k·Bc` → stride \(B_c = 32\) → \(W = 32\). It **moves** the conflict from \(D\) reads/warp/tile to \(D\) writes/warp/tile. Same count, same \(W\), zero net gain, plus an indexing rewrite.

**XOR swizzle,** `sK[tx*D + (d ^ (tx & 31))]`. Also conflict-free and costs zero extra bytes, but needs the identical XOR on both sides and is much harder to read. Kept as a fallback if the 128 bytes ever matter.

**Padding wins** because it makes *both* sides conflict-free for 128 bytes and one changed constant.

## 6. Change 2 — `Õ` from shared memory into registers

### 6.1 Why it's legal

v1's STEP 7 reads and writes `sO[ty*D + d]` for exactly \(d \in \{t_x, t_x + B_c, \dots\}\). **No other thread touches those elements, in any step, in any tile iteration.** `sO` is thread-private state living in a shared buffer — it's there because an array is the obvious place to put an accumulator, not because the data flow requires sharing.

So the transformation is a pure lift into a per-thread register array of length

\[
L = \frac{D}{B_c} = \begin{cases} 1 & D = 32 \\ 2 & D = 64 \\ 4 & D = 128 \end{cases}
\]

indexed by \(k\), where \(d = t_x + k B_c\).

### 6.2 The compile-time constraint that makes or breaks it

\(L\) must be a **compile-time constant**, or `ptxas` cannot allocate registers and puts the array in **local memory** — which is physically DRAM. The optimization would then invert into a serious pessimization.

v1 took `D` as a runtime `int`. **v2 must template on it**, which forces an explicit dispatch in the launch wrapper:

```cpp
switch (D) {
    case 32: launch_v2<32>(...); break;
    case 64: launch_v2<64>(...); break;
    default: /* error */
}
```

This is the single easiest way to get M6 wrong, and it is silent — the kernel still produces correct answers, just slowly.

### 6.3 What it buys

- **Shared memory freed:** \(4 B_r D = 8192\) B at \(D=64\) — 22% of v1's budget. This is what makes §7 and (later) `D = 128` reachable.
- **Latency removed:** `LDS` is ~20–30 cycles on Turing; a register operand is ~0. At \(N=2048, D=64\) that's \(T_c \cdot L \cdot 2 = 256\) shared accesses per thread eliminated.
- **Register cost:** \(L\) registers per Q row, so \(2L = 4\) at \(D = 64\) once §7's coarsening lands. Negligible.

This change is the **keystone**: it unlocks the occupancy work in §7 and the `D = 128` path in M7.

## 7. Change 3 — 512 threads per CTA, two Q rows per thread

### 7.1 The Turing limits

| Resource | Limit per SM (sm_75) |
|---|---|
| Threads | 1024 |
| Warps | 32 |
| Registers | 65,536 |
| Shared memory | 64 KB |
| Resident CTAs | 16 |

Note Turing halved max warps/SM to 32 (Volta had 64).

### 7.2 v1's occupancy, and why the number lies

\[
\text{CTAs/SM} = \min\!\left(\left\lfloor\tfrac{1024}{1024}\right\rfloor,\ \left\lfloor\tfrac{65536}{1024 R}\right\rfloor,\ \left\lfloor\tfrac{65536}{37120}\right\rfloor,\ 16\right) = 1
\]

**Exactly one CTA per SM**, and the *thread* limit alone forces it. That CTA has 32 warps, so theoretical occupancy reads **100%**.

That number is misleading, and here is the failure mode it hides. v1 executes `__syncthreads()` three times per tile iteration. At a barrier, all 32 resident warps must arrive before any proceeds. With one CTA per SM, **the SM has nothing else to issue** — all four warp schedulers idle. Every stall (an LDG waiting on DRAM, a conflicted LDS replaying 32×) is fully exposed to wall-clock time.

```
   ONE CTA per SM (v1)                 TWO CTAs per SM (v2)
   CTA A: ████░░░░████░░░░             CTA A: ████░░░░████░░░░
                                       CTA B: ░░░░████░░░░████
   SM:    ████░░░░████░░░░             SM:    ████████████████
          ↑ idle at every barrier             ↑ never idle
```

A Turing SM has 4 partitions, each with its own scheduler picking **one ready warp per cycle** from its pool of 8. v1 fills every pool with 8 warps that are contractually obliged to freeze together. From a scheduler's view, that behaves like a single very wide warp.

**Both configurations have 32 warps/SM and 100% occupancy.** The only difference is the number of *independent barrier domains*: 1 vs 2. That is why the Nsight metric to prove is **not** `achieved_occupancy` — it's the stall-reason breakdown (barrier stalls) and the fraction of cycles a scheduler had nothing eligible.

### 7.3 The register-budget subtlety (get this right)

A tempting but **wrong** claim: "512-thread blocks double the per-thread register budget." They don't. The register file is one physical block:

\[
\text{registers/thread} \times \text{resident threads} \le 65{,}536 \quad \text{always}
\]

Two CTAs × 512 threads = 1024 resident threads = **still 64 registers each**, exactly as with one CTA of 1024. Grouping doesn't create registers.

The causality runs the other way: **`ptxas` picks \(R\) at compile time, and \(R\) then constrains how many CTAs can be resident.**

| block size | \(R\) chosen | CTAs/SM | resident threads | occupancy |
|---|---|---|---|---|
| 1024 | ≤ 64 | 1 | 1024 | 100% |
| 1024 | 65+ | **0 — won't launch** | — | — |
| 512 | ≤ 64 | 2 | 1024 | 100% |
| 512 | 65–128 | 1 | 512 | 50% |
| 512 | 129+ | 0 — won't launch | — | — |

**The real benefit is an escape hatch, not more registers.** At 1024 threads there are only two outcomes: fit in 64 registers, or don't launch. A kernel that naturally wants 80 registers *must* be squeezed to 64, and the squeezing mechanism is **spilling to local memory** — expensive inside a hot loop, and invisible to occupancy metrics. At 512 threads, `ptxas` can instead take 80 registers and drop to 1 CTA/SM: lower occupancy, but no spills. Which is better is empirical; at least the choice exists.

This is exactly why `docs/ptxas_v1_vs_v2.md` is a checked-in M6 deliverable, and why the kernel declares its intent explicitly:

```cpp
__launch_bounds__(512, 2)   // 512 threads/CTA, want ≥2 CTAs resident
```

Without it, `ptxas` guesses. With it, the `-v` output reports honestly whether it hit the 64-register target without spilling.

### 7.4 The mapping

`block = (Bc=32, Br/2=16)` = 512 threads. Warp `ty` owns local Q rows `ty` and `ty + 16`:

```
   BEFORE: 1024 threads, 1 row each     AFTER: 512 threads, 2 rows each
   warp 0 ──→ row 0                     warp 0 ──→ rows 0 and 16
   warp 1 ──→ row 1                     warp 1 ──→ rows 1 and 17
      ⋮                                    ⋮
   warp 31 ─→ row 31                    warp 15 ─→ rows 15 and 31
```

Splitting by `kWarps = 16` (rather than `2*ty, 2*ty+1`) is deliberate: each warp still reads **one `sQ` row at a time**, so STEP 2's `sQ` access stays a broadcast.

Crucially this **preserves the warp-per-row invariant**, so the `__shfl_xor` reductions in STEPS 3 and 5 still work — a warp just runs two of them sequentially. That's why this 1-D coarsening is preferred over full 2-D register tiling (§14), which would demolish the reduction structure.

### 7.5 The free bonus: operand reuse

Coarsening also amortizes shared loads across the thread's two rows:

- **STEP 2:** `sK[tx][d]` is loaded once per `d` and multiplied into *both* rows' accumulators. sK traffic per Q row halves.
- **STEP 7:** `sV[c][d]` is loaded once per `(c, k)` and reused by both rows. sV traffic per Q row halves.

This requires loop restructuring — hoist the shared load out and put the row loop innermost:

```cpp
for (int d = 0; d < D; ++d) {
    const float k_d = sK[tx * (D+1) + d];      // one load...
    for (int rr = 0; rr < 2; ++rr)             // ...two consumers
        s_acc[rr] += sQ[q_local[rr] * D + d] * k_d;
}
```

### 7.6 The resulting occupancy

\[
\text{smem}(32,32,64) = 4\big[\underbrace{32\cdot64}_{sQ} + \underbrace{32\cdot65}_{sK} + \underbrace{32\cdot64}_{sV}\big] = 4 \cdot 6176 = 24{,}704\ \text{B}
\]

\[
\text{CTAs/SM} = \min\!\left(\left\lfloor\tfrac{1024}{512}\right\rfloor,\ \left\lfloor\tfrac{65536}{512R}\right\rfloor,\ \left\lfloor\tfrac{65536}{24704}\right\rfloor,\ 16\right) = \min(2,\ \cdot,\ 2,\ 16) = \mathbf{2}
\]

At \(D = 32\): 12,416 B, also 2 CTAs. Both fit the 48 KB default per-CTA cap with no `cudaFuncSetAttribute` opt-in.

## 8. Change 4 — `float4` vectorized loads

### 8.1 Be honest about the size of this one

v1's STEP 1 load, for fixed `k`, has the warp read `K[b,h,j,tx + k·32]` — **32 consecutive floats = 128 contiguous bytes = exactly one fully-used cache line, zero wasted bytes.** v1's global loads are already perfectly coalesced. `float4` **cannot** reduce HBM bytes.

What it reduces is **instruction count**:

\[
\underbrace{2\cdot\tfrac{D}{B_c} = 4}_{\text{v1, scalar}} \longrightarrow \underbrace{2\cdot\tfrac{D}{4B_c} = 1}_{\text{float4}} \quad\text{LDG per warp per tile at } D=64
\]

A 4× cut in memory instructions and the address arithmetic behind them. But §3.1 established DRAM is ~1.8% of the runtime, so the direct win is ~2%. **This is the least valuable of the four changes**, which is worth stating because the M4 backlog lists it *first* and it is the thing most people reach for.

Its real value is second-order: fewer instructions means fewer issue slots and fewer live address registers, which helps the §7.3 register question.

### 8.2 Constraints and the mapping

`float4` needs 16-byte alignment. \(D \bmod 4 = 0\) makes every row start aligned given an aligned base (guaranteed by `cudaMalloc` and torch's allocator). Since v2 supports only \(D \in \{32,64\}\), \(D \bmod 4 = 0\) always holds — **the scalar fallback path the backlog proposed is dead code; don't write it.**

The naive mapping (thread `tx` loads floats \(4t_x..4t_x+3\)) needs only \(D/4 = 16\) lanes at \(D=64\), idling half the warp. Use a **linearized** loop over the tile's `float4` count instead:

```cpp
for (int v4 = tid; v4 < Bc * (D/4); v4 += kThreads) {
    const int r = v4 / (D/4), c4 = v4 % (D/4);
    ...
}
```

This also removes v1's hidden `Br == Bc` coupling (`flash_attention_notes.md` §11) — a **prerequisite** for ever exploring asymmetric tiles. Two backlog items, one edit.

### 8.3 One wrinkle the padding creates

`sK`'s padded stride \(D+1\) is odd, so a `float4` *store* into `sK` would be misaligned. Scatter four scalars instead:

```cpp
float* dst_k = sK + r * (D+1) + 4 * c4;
dst_k[0] = kk.x; dst_k[1] = kk.y; dst_k[2] = kk.z; dst_k[3] = kk.w;
```

Those scalar stores carry a mild 2-way bank conflict on ~8 stores per warp per tile. Against the 2048-wavefront read conflict the padding removes, that is a trade worth making by a factor of ~100. `sV` keeps its natural stride \(D\), so its `float4` store stands.

## 9. Change 5 — `P` never reaches shared memory

This one is not in the M4 backlog; it falls out of the warp-geometry audit in §5.1.

v1's STEP 5 writes `sS[ty*Bc + tx]` and STEP 7 reads `sS[ty*Bc + c]` for \(c = 0..B_c-1\). Since a warp is exactly the 32 lanes at fixed `ty`, **every element STEP 7 reads was written by a lane of the same warp.** The round trip through shared memory can be a register shuffle:

```cpp
const float p_c = __shfl_sync(0xffffffffu, p_val[rr], c);
```

What this buys:

- **4 KB of shared memory** (\(4 B_r B_c\)) freed.
- **One `__syncthreads()` per tile removed.** v1's barrier before STEP 7 was justified by a comment claiming STEP 7 "reads elements of `sS` that other warps' lanes just wrote" — which isn't so; row `ty`'s data never leaves warp `ty`. The other STEP-7 operand, `sV`, is already covered by the barrier after STEP 1.
- **Strictly safer than removing the barrier while keeping `sS`.** With no shared array there is no cross-warp hazard to reason about at all. Deleting a barrier is the highest-risk category of CUDA change; deleting the *buffer* removes the hazard by construction rather than by argument.

The same reasoning applies to `sm` and `sl`: both warp reductions **broadcast** their result to every lane, so all 32 lanes can hold bit-identical `(m, ℓ)` in registers and update them redundantly. No shared memory, no `tx == 0` write-back, no barrier.

Net barrier count per tile iteration: **v1 = 3, v2 = 2** (one guarding the `sK`/`sV` overwrite, one publishing the freshly loaded tile).

## 10. The tile-size fork we did *not* take

\(B_r\) is the **only** knob that changes HBM traffic (`M4.md` §10):

\[
\text{HBM} = 2ND + \frac{2N^2D}{B_r}\ \text{floats}, \qquad \frac{\text{HBM}_{\text{naive}}}{\text{HBM}_{\text{flash}}} \xrightarrow{N\to\infty} \frac{2B_r}{D}
\]

At \(B_r=32, D=64\) that ratio is \(1\times\) — parity with naive. Doubling to \(B_r = 64\) makes it \(2\times\), a genuinely quotable number for M9's roofline.

Two things block it, and they have to be taken in order.

**First, the thread count.** Threads/CTA is \(B_c \cdot (B_r / R)\). Holding \(R = 2\), going to \(B_r = 64\) gives 32 warps = **1024 threads**, which lands us straight back in v1's one-CTA-per-SM trap by the thread limit alone. To keep 512 threads you must also raise \(R\) to 4 — each thread then owns four Q rows and \(4L = 8\) accumulator registers, which is still cheap.

**Second, and this is the one that actually decides it, shared memory.** With \(R = 4\) restoring the 512-thread block, v2's layout at \(B_r = 64, D = 64\) needs

\[
\text{smem} = 4\big[\underbrace{64\cdot64}_{sQ} + \underbrace{32\cdot65}_{sK} + \underbrace{32\cdot64}_{sV}\big] = 4 \cdot 8224 = 32{,}896\ \text{B}
\]

One CTA fits the 48 KB cap comfortably. Two need **65,792 B against T4's 65,536** — over by **256 bytes**. It is that close, and it is worth being precise rather than hand-wavy about it, because the margin suggests obvious-looking rescues that don't survive contact:

- Dropping the `sK` padding for an XOR swizzle (§5.6) saves exactly \(B_c\) floats = 128 B/CTA = 256 B for two, landing on 65,536 — *exactly* the limit, with zero headroom for anything else the kernel might later need. Not a design to build on.
- At \(D = 32\) the problem evaporates (16,512 B/CTA, 33,024 B for two). So the fork is **`D`-dependent**, and any future \(B_r = 64\) path would have to be `D`-specialized rather than universal.

```
     Taller tile (Br = 64)              2 CTAs per SM (Br = 32)
     ─────────────────────              ───────────────────────
     halves DRAM traffic                hides the barrier stalls
              │                                   │
     but DRAM is 1.8% of runtime        but this attacks the 98%
              │                                   │
         ~1% faster                         ~20-50% faster
```

**Decision: `Br = 32`, two CTAs/SM.** Optimize the 98%, not the 1.8%. Keeping \(B_r\) at 32 has a second benefit for the writeup: v2's analytical HBM traffic is **identical to v1's by construction**, so any measured DRAM-throughput delta between them is unambiguously an efficiency effect, not a different traffic budget.

**This prediction is on the record before measuring.** It is also likely to *reverse* on A10G (Ampere, ~100 KB smem/SM, where both fit at once) — which is itself an interesting result to report, and the reason `AGENTS.md` §2.2 still wants filling in.

## 11. The resulting kernel, step by step

```
grid  = ( Tr = ⌈N/Br⌉,  B*H,  1 )
block = ( Bc = 32,       Br/RowsPerThread = 16,  1 )        → 512 threads
smem  = 4 * (Br*D + Bc*(D+1) + Bc*D)  bytes                 → 24,704 B at D=64
```

Shared memory holds **only** `sQ`, `sK` (padded), `sV`. Everything else — `(m, ℓ, Õ, p̃)` — is registers.

**Init.** Load the Q-tile once with vectorized linearized loads. Zero the register accumulators; seed \((m,\ell) = (-\infty, 0)\).

**Per KV-tile:**

| Step | What happens | Where operands live |
|---|---|---|
| barrier | guard previous iteration's `sV` readers | — |
| 1 | vectorized K/V load → `sK` (scalar scatter, padded), `sV` (`float4`) | HBM → smem |
| barrier | publish the tile | — |
| 2 | `s_acc[rr] += sQ[row_rr][d] * sK[tx][d]` — `sK` read once, both rows consume | smem (broadcast + conflict-free) → regs |
| — | apply scale + range + causal mask → `s_val` | regs |
| 3 | `warp_reduce_max` → `m_local` | regs (shuffle) |
| 4 | `m_new`, `α` with the `-inf` guards | regs |
| 5 | `p̃ = exp(s − m_new)`; `warp_reduce_sum` → `ℓ_local` | regs (shuffle) |
| 6 | `ℓ ← α·ℓ + ℓ_local`, `m ← m_new` — every lane, redundantly | regs |
| 7 | `acc_o[rr][k] ← α·acc_o[rr][k] + Σ_c p̃[rr][c]·sV[c][d]`, `p̃` via `__shfl_sync`, `sV` loaded once per `(c,k)` and reused by both rows | regs + smem (conflict-free) |

**Terminal.** `O[i, d] = acc_o / ℓ` (or 0 if `ℓ ≤ 0`), scalar coalesced stores, tail rows skipped.

### 11.1 Why the terminal store stays scalar

Thread `(tx, ty)` owns \(d = t_x, t_x + B_c, \dots\), so lanes cover consecutive `d` → the store is coalesced. A `float4` store would need each thread to own 4 *consecutive* `d`, which would make STEP 7's `sV` read lane-strided by 4 → \(\gcd(4,32) = 4\)-way conflict. That trades a conflict-free read in the hot loop for a marginally faster write that happens once per CTA. Not worth it.

## 12. Correctness argument

M6 changes no algebra, so the M4 correctness chain carries over unchanged, with one addition: **v2 must also match v1 directly.**

```
    PyTorch SDPA
        ⇕  ← M1 (1e-5 abs)
    NumPy ref (fp64)
        ⇕  ← M1
    C++ CPU ref  ──────┬──────────────┬──────────────┬──────────────
        ⇕ M2 (5e-4)    │ M3 (1e-5)    │ M4 (5e-4)    │ M6 (5e-4)
    Naive CUDA          Online-ref     Flash v1  ⇕⇕⇕  Flash v2
                                                 M6 parity (1e-5)
```

**Tolerance vs CPU ref: `5e-4` abs**, identical to M4 — v2 introduces no new axis of accumulation, so the bound must not move. If it ever needs loosening, the change was not the mechanical one it claims to be.

**Tolerance vs v1: `1e-5` abs**, deliberately tighter. Both kernels sum the `D` axis and the `Bc` axis in the same order, so they should differ only by FMA-contraction round-off, not algebra. They are **not** expected to be bit-identical: v2 reassociates the two Q rows' dot products into one loop and reads `V` through registers, which lets the compiler contract differently.

Three places a v2-specific bug can enter, and the test that catches each:

1. **The `RowsPerThread` row split.** A wrong `q_local`/`i_glob` mapping poisons half the rows. Caught by `N = 17` (exactly one `rr = 1` row live, fifteen tail-padded) — a configuration v1 could not produce.
2. **The padded `sK` stride.** Mixing `D` and `D+1` between the store and the load reads the wrong element. Caught by the whole grid immediately.
3. **The restructured mask.** v2 applies the causal/range predicate to the accumulated score rather than gating the dot-product loop. Caught by the tails (`N = 100`, `N = 257`) and the causal smoke test.

## 13. Predictions, written down before measuring

At \(N = 2048, D = 64\) on T4, from 11.65 ms:

| Change | Mechanism | Predicted |
|---|---|---|
| 1. Padded `sK` | 2252 → 268 wavefronts/warp/tile | **3–5×** |
| 2. `Õ` → registers | −8 KB smem, −256 LDS/thread | 1.05–1.15× |
| 3. 512 threads → 2 CTAs/SM | barrier convoy broken | 1.2–1.5× |
| 4. `float4` loads | 4× fewer LDG | 1.0–1.05× |
| 5. `P` via shuffle | −4 KB smem, −1 barrier/tile | 1.05–1.1× |
| **Combined** | | **~4–7× → 1.7–2.9 ms** |

They don't multiply cleanly: once the biggest bottleneck goes, the second-biggest becomes the limit (probably barrier stalls, then the LDS-per-FMA ratio in §14.1).

**The bar that matters.** MILESTONES asks for "faster than v1 at \(N \ge 512, D = 64\)". The more meaningful bar is **beating `attention_naive` at \(N = 2048, D = 64\)** — v1 currently *loses* there (11.65 ms vs 6.66 ms), and the repo's whole thesis depends on Flash winning at large `N`.

**The metric that must move.** `l1tex__data_bank_conflicts_pipe_lsu_mem_shared` should drop by roughly the 8.4× predicted in §5.5. Not `achieved_occupancy` — that reads 100% both before and after (§7.2).

## 14. Still deferred after v2 — the v3 backlog

### 14.1 2-D register blocking of the S matmul — the biggest remaining lever

Even conflict-free, STEP 2 issues **2 `LDS` per `FFMA`** (one `sQ`, one `sK`). Turing retires 64 FP32 FMA/cycle but only ~1 warp-wide `LDS`/cycle, so the arithmetic *cannot* saturate — the shared-memory pipe is the limiter by construction.

The textbook fix has each thread compute a \(t \times t\) micro-tile of \(S\):

\[
\frac{\text{LDS}}{\text{FMA}} = \frac{2t}{t^2} = \frac{2}{t}
\]

A \(2\times2\) tile gives 1, a \(4\times4\) gives 0.5. §7's 1-D coarsening already captures part of this (`sK` shared across 2 rows → 1.5 LDS/FMA).

**Why not in M6:** a 2-D micro-tile breaks the warp-per-Q-row invariant that the `__shfl_xor` reductions depend on, requiring STEPS 3 and 5 to be redesigned as cross-lane partial reductions. That's a rewrite, not a tuning pass, and it collides with M6's stated scope. This is the honest answer to checkpoint #2.

### 14.2 Everything else

- **Async copies (`cp.async`)** — Ampere+; T4 is Turing. Needs double-buffered smem and a pipelined block loop. M7 at the earliest, gated on `sm_86`.
- **FA-2 loop reversal** — out of scope for `v1.0.0`; named in M10's "reading the gap."
- **`D = 128`** — now within reach on the smem budget (§6 freed 8 KB) but still needs the 64 KB `cudaFuncSetAttribute` opt-in. M7.
- **Batch / multi-head / causal grids** — kernel supports all three; formal grids are M7.
- **Tensor cores / WMMA** — explicit anti-scope (`AGENTS.md` §10).
- **Small-`N` under-utilization** — a launch-config problem (4 CTAs on 40 SMs at `N=128`), unfixable by anything in M6.

## 16. Understanding checkpoint (answer these out loud)

1. **Which of bank conflicts / occupancy / vectorized bandwidth actually moved the needle, and which metric proves it?** The bank-conflict fix, by a wide margin — one line (`sK[tx*D + d]`, lane-stride \(D\), \(W = \gcd(64,32) = 32\)) was 91% of all shared-memory wavefronts. `l1tex__data_bank_conflicts_pipe_lsu_mem_shared` is the metric; predicted ~8.4× drop. Vectorized bandwidth was always going to be small because v1's loads were already perfectly coalesced and DRAM was 1.8% of runtime.

2. **Why is "100% occupancy" not the same as "the SM is busy"?** Occupancy counts resident warps, not independent ones. v1's 32 warps are one CTA that freezes together at every `__syncthreads()`, leaving all four schedulers with nothing to issue. Two CTAs of 512 threads give the same 32 warps and the same 100%, but two independent barrier domains.

3. **Does halving the block size double the per-thread register budget?** No. \(R \times \text{resident threads} \le 65{,}536\) always; 2 × 512 = 1024 threads is still 64 registers each. What halving buys is a *fallback*: at 1024 threads the only alternative to 64 registers is spilling, whereas at 512 `ptxas` can take up to 128 and drop to one CTA. The `ptxas -v` output decides which regime we're in.

4. **What breaks if `D` stays a runtime argument?** `L = D/Bc` stops being compile-time, `ptxas` can't allocate `acc_o[][]` in registers, and the "register-resident `Õ`" array lands in local memory (physically DRAM) inside the hot loop. The kernel stays *correct* and gets *slower* — a silent failure, which is why it's called out in §6.2.

5. **Why is `sV` conflict-free in STEP 7 when `sK` isn't in STEP 2?** In STEP 2 the lane index `tx` multiplies \(D\) (`sK[tx*D + d]`), giving stride \(D\). In STEP 7 the lane index enters through `d = tx + k·Bc` while `c` is a uniform loop counter, giving stride 1. The M4 backlog got this backwards (§5.2).

6. **What did you *not* fix that you'd fix in v3?** 2-D register blocking of the S matmul (§14.1). Even conflict-free it's 2 `LDS` per `FFMA`, so shared memory still gates the math. Fixing it breaks the warp-per-row reduction structure — a rewrite, not a tuning pass.

## 17. Glossary

| Term | Meaning |
|---|---|
| **Bank** | One of 32 independently-addressable slices of shared memory. `bank(a) = a % 32` with `a` in floats. |
| **Lane** | A thread's index *within its warp*, 0–31. Equals `tx` here because `blockDim.x == 32`. |
| **Wavefront** | One cycle's worth of a shared-memory instruction. \(W = \gcd(\text{lane-stride}, 32)\), or 1 for a broadcast. |
| **Bank conflict** | \(W > 1\): several lanes want different addresses in the same bank, serialized. |
| **Broadcast** | All 32 lanes want the *same* address; served in one wavefront, free. |
| **Padding (+1)** | Growing a tile's leading dimension by one float to make the lane-stride odd, hence \(\gcd = 1\). |
| **Occupancy** | Resident warps ÷ max warps per SM. Counts residency, *not* independence — see §7.2. |
| **Barrier domain** | The set of warps that must rendezvous at a `__syncthreads()`. One per CTA; more CTAs = more independence. |
| **Register spilling** | `ptxas` running out of registers and moving values to *local memory* (physically DRAM). Invisible to occupancy metrics; visible in `ptxas -v`. |
| **`__launch_bounds__(T, B)`** | A promise to `ptxas`: ≤ `T` threads/CTA, and please fit ≥ `B` CTAs per SM. Constrains its register target. |
| **`L`** | `D / Bc` — the number of register accumulator slots each thread holds per Q row. Must be compile-time. |
| **`RowsPerThread`** | Q rows owned by one thread. 2 in v2, which is what halves the thread count. |
| **Flash v2 (ours)** | Mechanical retune of M4's kernel. **Not** FlashAttention-2 the paper — see §2. |
