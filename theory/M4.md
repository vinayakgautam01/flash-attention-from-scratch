## 1. The one-sentence goal of M4

> **Compute the whole attention forward pass in a single fused kernel by tiling `Q` into `Br`-row blocks and streaming `K`/`V` in `Bc`-column blocks, so `S` and `P` never touch HBM.**

Everything else in M4 — the `(Br, Bc)` picks, the CTA grid, the shared-memory layout — is *engineering* on top of one algorithmic idea: **run M3's online-softmax recurrence for `Br` query rows simultaneously**, so each `K`/`V` tile loaded from HBM amortizes across `Br` rows instead of `1`.

If M3 was "prove the streaming recurrence works" (`theory/M3.md` §1), M4 is *"run that recurrence in parallel for `Br` rows and never let `S` or `P` escape the SM."*

---

## 2. What M4 is *not*

Bounding scope up-front prevents scope creep:

- **Not multi-head, not batched (yet).** `B = 1, H = 1`. The `[B, H, N, D]` layout stays and the API carries the `(b, h)` axes, but the tests only exercise the interesting axes. Batching + multi-head land in M7 — mechanically, that's a `grid.y = B*H` change and nothing else.
- **Not causal (yet).** Kernel plumbs an `is_causal` flag but tests skip it. Causal correctness on the diagonal tile (where the mask crosses inside a single KV-tile) is M7.
- **Not fp16.** M4 is fp32 in, fp32 accumulate, fp32 out. Mixed precision is M8.
- **Not layout-optimized.** No `float4` loads, no shared-memory swizzling, no bank-conflict fights, no register-pressure tuning, no `ptxas -v` chase. That's the entire point of M6. If you catch yourself pattern-matching to "let me use `float4` here" while writing M4, stop and write it in `docs/flash_attention_notes.md` as a v2 candidate.
- **Not `D ∈ {128}`.** M4 targets `D ∈ {32, 64}` only. `D = 128` is a shared-memory-budget conversation that lands with M7.
- **Not a benchmarking milestone.** The one-plot deliverable in M4 is a runtime-vs-`N` comparison against `attention_naive`; the harness proper (median-of-N, warm-up, CSV schema) is M5.

The **only** correctness delta from M3 is the second axis of tiling (`Br` rows). If M3 is right, the M4 kernel is `M3-with-a-second-loop`. That's the whole conceptual budget.

## 3. Refresher: what M3 gave us, and where it still bleeds bandwidth

From `theory/M3.md` §7.4, for a single query row `i`, the block loop looks like:

Given running state $(m_i, \ell_i, \tilde{O}_i)$ before block $b$ and this block's slice $\{K_j, V_j\}_{j \in b}$:

$$
\begin{aligned}
s_{i,j} &= \tfrac{1}{\sqrt{D}}\, Q_i \cdot K_j, \quad j \in b \\
\tilde{m}_i &= \max_{j \in b} s_{i,j} \\
m_i^{\text{new}} &= \max(m_i,\, \tilde{m}_i) \\
\alpha_i &= \exp(m_i - m_i^{\text{new}}) \in (0, 1] \\
\tilde{p}_{i,j} &= \exp(s_{i,j} - m_i^{\text{new}}), \quad j \in b \\
\ell_i^{\text{new}} &= \alpha_i \cdot \ell_i + \sum_{j \in b} \tilde{p}_{i,j} \\
\tilde{O}_i^{\text{new}} &= \alpha_i \cdot \tilde{O}_i + \sum_{j \in b} \tilde{p}_{i,j} \cdot V_j
\end{aligned}
$$

with terminal $O_i = \tilde{O}_i / \ell_i$.

M3's kernel runs *one CTA per query row*. Two problems with that as-is:

1. **`K` and `V` are re-fetched from HBM for every query row.** Each of the `N` CTAs loads the same `N/Bc` blocks of `K` and `V`. Total HBM reads of `K` and `V`: `2·N²·D` floats. That's what M4 attacks.
2. **Occupancy is bounded by "one CTA does one row".** Small CTAs (each with only `Bc = 64` threads) may not saturate the SM.

The fix for (1) is what M4 is about. Fix for (2) is a partial free lunch on the way there, then finished in M6.

## 4. The core idea: two levels of tiling

Cut both the query axis and the key axis into tiles:

- **Q-tile size $B_r$** — rows of `Q` handled by one CTA. Typical $B_r \in \{32, 64\}$.
- **K/V-tile size $B_c$** — columns of `K`/`V` streamed per inner-loop iteration. Typical $B_c \in \{32, 64\}$.

Let $T_r = \lceil N / B_r \rceil$ and $T_c = \lceil N / B_c \rceil$.

**One CTA owns one Q-tile** — a contiguous stripe of `Br` output rows $O_{[i_0 : i_0 + B_r], :}$ where $i_0 = \text{blockIdx.x} \cdot B_r$.

Inside a CTA, `Br` independent copies of M3's `(m, ℓ, Õ)` state run in lock-step over the same sequence of $K/V$ tiles. **Every $K/V$ load is amortized over $B_r$ query rows.**

M3 vs M4 side-by-side:

```
             per query row (M3)           per Q-tile of Br rows (M4)
           ┌──────────────────┐         ┌────────────────────────────┐
grid       │ N CTAs           │         │ Tr = ⌈N/Br⌉ CTAs           │
           ├──────────────────┤         ├────────────────────────────┤
state kept │ (m, ℓ, Õ)        │         │ Br × (m, ℓ, Õ)             │
per CTA    │ = D+2 floats     │         │ = Br·(D+2) floats          │
           ├──────────────────┤         ├────────────────────────────┤
K/V loads  │ per CTA: 2·N·D   │         │ per CTA: 2·N·D             │
           │ (× N CTAs)       │         │ (× Tr CTAs)                │
total K/V  │ 2·N²·D floats    │         │ 2·N²·D / Br floats         │  ← Br× fewer
```

That last row is the whole HBM win. Formal accounting in §10.

### 4.1 Grid vs loop — the confusion trap

The two tiling axes reach the CTA through **different mechanisms**, and mixing them up is the single most common M4 bug:

- **Q axis → CTA-level parallelism.** Tiled by *launching more CTAs*. `grid.x = Tr`. Each CTA sees its slot via `blockIdx.x`.
- **K/V axis → intra-CTA serial loop.** Tiled by *iterating inside the kernel*. `for b_idx in 0..Tc`. Each iteration reuses the same CTA, the same threads, the same shared memory.

```
                        KV-tile 0        KV-tile 1
                        (j: 0..Bc-1)     (j: Bc..2Bc-1)
                    ┌────────────────┬────────────────┐
   CTA 0            │  iter b_idx=0  │  iter b_idx=1  │      → writes O[0..Br-1, :]
   blockIdx.x = 0   │                │                │
                    └────────────────┴────────────────┘

                    ┌────────────────┬────────────────┐
   CTA 1            │  iter b_idx=0  │  iter b_idx=1  │      → writes O[Br..2Br-1, :]
   blockIdx.x = 1   │                │                │
                    └────────────────┴────────────────┘

     Different CTAs (parallel)        Same CTA, sequential loop
```

**`blockIdx.x` is fixed for the CTA's lifetime.** It is *not* the loop counter. The loop counter `b_idx` is a plain `int` local variable inside the kernel.

## 5. The math — `Br`-parallel online softmax

The recurrence in §3 is **per-row**. Nothing about it couples two different query rows `i` and `i'` — their scores `s_{i,:}` and `s_{i',:}` are independent, their running maxes independent, everything independent. So we can run `Br` copies of the recurrence in parallel with no algebraic changes.

Written matrix-flavored, for a Q-tile of rows $[i_0, i_0 + B_r)$ and a K/V-tile of columns $[j_0, j_0 + B_c)$:

Let $Q^{(r)} \in \mathbb{R}^{B_r \times D}$ be the current Q-tile, $K^{(c)}, V^{(c)} \in \mathbb{R}^{B_c \times D}$ be the current K/V-tile, and let $(m, \ell, \tilde{O})$ be the running state — one row per Q-row, so shapes $\mathbb{R}^{B_r}$, $\mathbb{R}^{B_r}$, $\mathbb{R}^{B_r \times D}$.

The per-tile update is:

$$
\begin{aligned}
S^{(rc)} &= \tfrac{1}{\sqrt{D}}\, Q^{(r)} \, {K^{(c)}}^{\top} \in \mathbb{R}^{B_r \times B_c} \\
\tilde{m} &= \mathrm{rowmax}\big(S^{(rc)}\big) \in \mathbb{R}^{B_r} \\
m^{\text{new}} &= \max(m,\, \tilde{m}) \\
\alpha &= \exp(m - m^{\text{new}}) \in \mathbb{R}^{B_r}, \quad \alpha \in (0, 1]^{B_r} \\
\tilde{P}^{(rc)} &= \exp\!\big(S^{(rc)} - m^{\text{new}}\otimes \mathbf{1}^{\top}_{B_c}\big) \in \mathbb{R}^{B_r \times B_c} \\
\ell^{\text{new}} &= \alpha \odot \ell + \mathrm{rowsum}\big(\tilde{P}^{(rc)}\big) \\
\tilde{O}^{\text{new}} &= \mathrm{diag}(\alpha)\cdot \tilde{O} + \tilde{P}^{(rc)} \, V^{(c)} \\
m &\leftarrow m^{\text{new}}, \quad \ell \leftarrow \ell^{\text{new}}, \quad \tilde{O} \leftarrow \tilde{O}^{\text{new}}
\end{aligned}
$$

Here $\odot$ is elementwise (Hadamard) and $m^{\text{new}} \otimes \mathbf{1}^{\top}$ broadcasts the `Br` running maxes across the `Bc` columns of $S^{(rc)}$.

Two things worth stating explicitly:

- The `Br × Bc` block $S^{(rc)}$ **exists only in shared memory / registers**. It is born inside the CTA and dies inside the CTA. That is *exactly* the "S never touches HBM" property from the FlashAttention paper — you can point at the specific line where it goes out of scope.
- The `Br × Bc` block $\tilde{P}^{(rc)}$ is the same story. It exists briefly, feeds two consumers (`rowsum` to update `ℓ`, and the `P V` matmul to update `Õ`), and dies.

**Terminal (after all $T_c$ tiles processed):**

$$
O^{(r)} = \mathrm{diag}(\ell)^{-1} \cdot \tilde{O} \in \mathbb{R}^{B_r \times D}
$$

Write $O^{(r)}$ to $O_{[i_0 : i_0 + B_r], :}$ in HBM. Done. That's the only HBM write this CTA performs.

## 6. Two loops, two nesting choices (why M4 picks Option A)

There are two natural loop orderings for the two tiling axes. FA-1 chose one, FA-2 chose the other, and M4 has to pick one intentionally.

**Option A (FA-1 style — what M4 uses):**

```
for i_tile in 0..Tr:              ← parallel across CTAs (grid.x)
    load Q_tile from HBM          ← once per CTA
    init (m, l, Õ) = (-∞, 0, 0)
    for b_idx in 0..Tc:           ← serial inside a CTA
        load K_tile, V_tile       ← Tc times per CTA
        S = Q_tile @ K_tile.T / √D
        merge (m, l, Õ) with block
    write O_tile
```

$K$ and $V$ are re-loaded $T_r$ times each in total; $Q$ and $O$ move exactly once.

**Option B (FA-2 style — deferred to future work, *not* M4):**

```
for j_tile in 0..Tc:              ← parallel across CTAs
    load K_tile, V_tile once
    for i_tile in 0..Tr:          ← serial (or partitioned) inside
        load Q_tile, running state
        merge into running state
        write updated state
```

$Q$ and the running state migrate more; $K, V$ move less. FA-2 does this with sequence-parallel work partitioning across CTAs; it's a scheduling change plus a merge step (the monoid combine from `theory/M3.md` §8). Out of scope for M4.

M4 picks **Option A** because:

- It keeps the algorithm change small (one extra outer loop over Q-tiles, mapped to CTAs — no cross-CTA synchronization).
- Per-CTA state stays local: no read-modify-write of the running `(m, ℓ, Õ)` from HBM.
- The `Br × ...` state fits easily in registers/shared memory for reasonable `Br`.

That's the tradeoff we own explicitly: **M4 re-reads K/V $T_r$ times.** Reversing that is future work, and we say so in `docs/flash_attention_notes.md` at the end of the milestone.

## 7. Shared-memory budget — the constraint that picks `(Br, Bc)`

The CTA needs to hold, at minimum:

| Buffer | Shape | Bytes (fp32) |
|---|---|---|
| `sQ` — Q-tile | `[Br, D]` | `4·Br·D` |
| `sK` — this KV-tile's K | `[Bc, D]` | `4·Bc·D` |
| `sV` — this KV-tile's V | `[Bc, D]` | `4·Bc·D` |
| `sO` — running `Õ` (smem for v1, registers in v2) | `[Br, D]` | `4·Br·D` |
| `sS` — scores/probabilities scratch | `[Br, Bc]` | `4·Br·Bc` |
| `sm`, `sl` — running max & normalizer | `[Br]` each | `8·Br` |

Upper-bound shared-mem cost (everything smem-resident):

$$
\text{smem}(B_r, B_c, D) = 4\big[\underbrace{2 B_r D}_{Q + \tilde O} + \underbrace{2 B_c D}_{K + V} + \underbrace{B_r B_c}_{S / \tilde P} + \underbrace{2 B_r}_{m, \ell}\big]
$$

**Colab T4 default per-CTA smem: 48 KB = 49,152 B.** Plug in candidate tile sizes:

| Br | Bc | D | smem (B) | Fits 48 KB? |
|---|---|---|---|---|
| 32 | 32 | 32 | `4·(2·32·32 + 2·32·32 + 32·32 + 64)` = `4·5184` = **20,736** | ✅ |
| 32 | 32 | 64 | `4·(2·32·64 + 2·32·64 + 32·32 + 64)` = `4·9280` = **37,120** | ✅ |
| 64 | 32 | 32 | `4·(2·64·32 + 2·32·32 + 64·32 + 128)` = `4·7296` = **29,184** | ✅ |
| 64 | 64 | 32 | `4·(2·64·32 + 2·64·32 + 64·64 + 128)` = `4·12416` = **49,664** | ❌ (over 48 K) |
| 64 | 32 | 64 | `4·(2·64·64 + 2·32·64 + 64·32 + 128)` = `4·14464` = **57,856** | ❌ |
| 64 | 64 | 64 | `4·(2·64·64 + 2·64·64 + 64·64 + 128)` = `4·20608` = **82,432** | ❌ (needs 64 K opt-in *and even then* too big) |

**M4 target on Colab T4: `Br = Bc = 32` for `D ∈ {32, 64}`.** One tile-size pick, both `D` values, all fits in 48 KB without a `cudaFuncSetAttribute` opt-in. That's the calculation that will live in the header comment of `csrc/flash_fwd_v1.cu`.

Also worth checking: threads-per-CTA. With `block = (Bc, Br)` (see §8), we have `Br * Bc = 32 * 32 = 1024` threads — exactly at CUDA's hard cap. Choosing `Br = Bc = 64` would need `4096` threads/CTA (impossible) — so the threads-per-CTA limit *and* the smem budget both push us to `Br = Bc = 32`. Not a coincidence.

Keeping $\tilde O$ in **registers** (one thread per output element, indexed by `(row, dim)`) would drop the `4·Br·D` term from the budget and buy headroom for larger tiles in v2 — that's an M6 knob we do *not* pull in v1.

The A10G budget in `docs/AGENTS.md` §2.2 is still `_pending_`; once M5's first Modal run fills it, we may revisit `(Br, Bc)` for A10G. For now, `Br = Bc = 32` is the M4 pick.

## 8. Launch configuration and grid mapping

```
grid  = ( Tr = ⌈N/Br⌉ ,   B*H ,   1 )
block = ( Bc,             Br ,    1 )
smem  = smem(Br, Bc, D)  bytes
```

Grid dim decoder — what each `blockIdx.*` tells the kernel:

```
blockIdx.x   → which Q-tile   (rows [i0 = blockIdx.x*Br, i0 + Br))
blockIdx.y   → which (batch, head), decoded as b = blockIdx.y / H, h = blockIdx.y % H
blockIdx.z   → unused (always 0)
```

Block dim decoder — what each `threadIdx.*` tells the kernel:

```
threadIdx.y  → my Q row inside the tile   (ty ∈ [0, Br))
threadIdx.x  → my K/V col inside the CURRENT KV-tile   (tx ∈ [0, Bc); changes every b_idx)
```

**Why `block = (Bc, Br, 1)` and not `(Br, Bc, 1)`?** Coalescing. Warps in CUDA are always contiguous along `threadIdx.x` first. When step 1 (§9) does the cooperative K/V load, threads in the same warp differ only in `tx`, so they read consecutive elements of `K[j, d]` for consecutive `j` — which is exactly what HBM likes. The `(Br, Bc, 1)` orientation would make the load look strided from HBM's point of view.

Total threads / CTA at `Br = Bc = 32`: 1024 (the CUDA max). We run **1024 / 32 = 32 warps per CTA.**

Because Colab T4 has 1024 max threads/SM, only **one CTA fits per SM** at this launch config. Occupancy on paper is `32 warps / 32 max = 100%`, but with only one CTA per SM the scheduler has less to hide latency behind. **This is a named v2 improvement** (M6 backlog, §13).

CTAs launched, canonical M4 shapes (`Br = 32`, `B = H = 1`):

| `N` | `Tr` | grid | Total CTAs |
|---|---|---|---|
| 128 | 4 | `(4, 1, 1)` | 4 |
| 256 | 8 | `(8, 1, 1)` | 8 |
| 512 | 16 | `(16, 1, 1)` | 16 |
| 1024 | 32 | `(32, 1, 1)` | 32 |
| 2048 | 64 | `(64, 1, 1)` | 64 |

T4 has 40 SMs. At `N = 512` only 16 SMs get work; at `N = 2048` all SMs run with room to overlap. **The "M4 under-utilizes small N" story** is another v2 backlog item.

## 9. Thread mapping inside one CTA — who does what per step

Fix `blockIdx.x`. This CTA owns Q-tile `i_tile` (rows `[i_tile*Br, i_tile*Br + Br)`). It sweeps `Tc` KV-tiles. Inside one tile iteration, seven steps happen in order, with `__syncthreads()` between steps that change what threads read.

Below, small example uses `Br = Bc = 4, D = 4` for concreteness; scaling to `Br = Bc = 32, D = 64` is bookkeeping only.

### STEP 1 — cooperative load of `sK`, `sV`

`Bc * D` elements to load. `Br * Bc` threads available. Threads iterate over the `D`-dimension in a loop when `D > Br` (real M4: `D = 64, Br = 32` → each thread loads 2 elements per tensor).

```
Thread (tx, ty)  performs, for d = ty, ty + Br, ty + 2*Br, ... < D:
    sK[tx, d] = K[b_idx*Bc + tx , d]
    sV[tx, d] = V[b_idx*Bc + tx , d]
```

Tail guard: if `b_idx*Bc + tx >= N`, load 0 (so the score becomes `-inf` via mask, and the `V` contribution becomes zero).

`__syncthreads()`.

### STEP 2 — score tile `sS = sQ · sK^T / √D`

Each thread computes **one element** of the `Br × Bc` score tile via a dot product along `D`. Here `ty` reverts to meaning "my Q row":

```
Thread (tx, ty):
    acc = 0
    for d in 0..D:
        acc += sQ[ty, d] * sK[tx, d]
    sS[ty, tx] = acc / √D
```

`__syncthreads()`.

### STEP 3 — row-max reduction → `m̃[ty]`

Reduction along `tx`, once per `ty`. Simplest scheme: each row does an independent block reduction using scratch shared memory. Since we have `Bc` threads per row (indexed by `tx`), the tree reduce is `log2(Bc)` steps.

```
Row 0 reduction:   threads (0..Bc-1, ty=0)   →   max over sS[0, :]   → m̃[0]
Row 1 reduction:   threads (0..Bc-1, ty=1)   →   max over sS[1, :]   → m̃[1]
...
```

`__syncthreads()`.

### STEP 4 — per-row `α`, `m_new`

Row-scalar work. One thread per row (`tx == 0`) is enough:

```
if (tx == 0):
    m_old        = sm[ty]
    m_new_row    = max(m_old, m̃[ty])
    alpha_row    = exp(m_old - m_new_row)   // guard: −∞ → 0, both-−∞ → 1
    salpha[ty]   = alpha_row
    sm_new[ty]   = m_new_row
```

`__syncthreads()`.

### STEP 5 — `p̃` tile, then row-sum → `ℓ̃[ty]`

Each thread converts its already-computed score into `p̃`, overwriting `sS`:

```
Thread (tx, ty):
    sS[ty, tx] = exp(sS[ty, tx] - sm_new[ty])   // 0 if j out of range / causal-masked
```

`__syncthreads()`. Then a second row-reduction (same shape as step 3), this time summing:

```
Row ty reduction:   sum over sS[ty, :]   → ℓ̃[ty]
```

`__syncthreads()`.

### STEP 6 — merge into running `(m, ℓ)`

Row-scalar work again:

```
if (tx == 0):
    sl[ty] = salpha[ty] * sl[ty] + ℓ̃_row
    sm[ty] = sm_new[ty]
```

`__syncthreads()`.

### STEP 7 — Õ update: `sO ← α · sO + p̃ · sV`

This is the big step: a `Br × D` matmul. Output has `Br * D` elements; we have `Br * Bc` threads. When `D <= Bc` (real M4: `D = 64, Bc = 32` → doesn't fit this constraint directly; when `D > Bc`, each thread produces `⌈D/Bc⌉` output elements in a loop). Here `tx` swings meaning: it becomes a `D`-index, **not** a K/V-col index.

```
Thread (tx, ty)  produces  Õ[ty, d]  for  d = tx, tx + Bc, ... < D:
    acc = salpha[ty] * sO[ty, d]
    for c in 0..Bc:
        acc += sS[ty, c] * sV[c, d]
    sO[ty, d] = acc
```

`__syncthreads()`.

### End-of-iteration handoff

The CTA loops to STEP 1 with `b_idx += 1`. `sK`, `sV`, `sS`, `salpha`, `sm_new` get overwritten. `sQ`, `sm`, `sl`, `sO` carry forward. Same 1024 threads, same seven steps, different source addresses.

### 9.1 The `tx` shape-shift is the whole thing to internalize

Different steps use `tx` to mean different things:

| Steps | What `tx` indexes | Why |
|---|---|---|
| 1, 2, 3, 5 (reduction phases) | **K/V column** `j` inside the KV-tile | We're computing scores against `Bc` keys |
| 4, 6 (row-scalar micro-steps) | Only `tx == 0` matters | Row-scalar work; other threads idle |
| 7 (Õ update) | **`D`-index** `d` for the output | We're computing `Br × D` output elements |

The `__syncthreads()` between numbered steps is what makes this legal: it lets us reinterpret `tx` from "K-col" to "D-dim" without data hazards. **This is the single most confusing thing on a first read.** If it's fuzzy, re-scan steps 3 and 7 side by side.

### 9.2 Terminal step — normalize and emit `O`

After the `Tc` iterations:

```
Thread (tx, ty)  writes  O[i_tile*Br + ty , d]  for  d = tx, tx + Bc, ... < D:
    O[..] = (sl[ty] > 0) ? sO[ty, d] / sl[ty] : 0
```

The only HBM writes this CTA ever performed are these `Br * D` floats. **`S` never touches HBM. `P` never touches HBM. `Õ` never touches HBM.**

## 10. HBM traffic accounting

Per CTA (Option A, §6):

| Operation | Floats |
|---|---|
| Load Q-tile once | `Br · D` |
| Load K-tile × `Tc` times | `Tc · Bc · D = N · D` |
| Load V-tile × `Tc` times | `Tc · Bc · D = N · D` |
| Write O-tile once | `Br · D` |
| **Per-CTA total** | `2·Br·D + 2·N·D` |

Total across all `Tr = N/Br` CTAs (single head, single batch):

$$
\text{HBM}_{\text{M4}} = T_r \cdot (2 B_r D + 2 N D) = 2 N D + \frac{2 N^2 D}{B_r} \text{ floats}
$$

Compare against the M2 naive path (redoing the sum for completeness):

$$
\text{HBM}_{\text{naive}} = \underbrace{2 N D}_{Q + K \text{ for QK}^T} + \underbrace{N^2}_{\text{write } S} + \underbrace{2 N^2}_{\text{softmax: read S, write P}} + \underbrace{N^2 + N D}_{\text{PV: read P, read V}} + \underbrace{N D}_{\text{write } O} = 4 N D + 4 N^2 \text{ floats}
$$

Ratio (large-`N`, single head):

$$
\frac{\text{HBM}_{\text{naive}}}{\text{HBM}_{\text{M4}}} \xrightarrow{N \to \infty} \frac{4 N^2}{2 N^2 D / B_r} = \frac{2 B_r}{D}
$$

Plugging M4's picks:

- `D = 32, Br = 32`: ratio = **2×** less HBM than naive.
- `D = 64, Br = 32`: ratio = **1×** — *parity*, not a win on paper.

Two things to hold in mind:

1. **Parity in HBM totals still translates to a runtime win**, because M4 avoids the *N²-sized allocations* of `S` and `P` entirely (peak alloc drops from ~`2·N²·4 B` to `O(smem/CTA)`), and because the naive HBM traffic is *latency-bound* (small transactions to intermediate buffers), whereas FA1's traffic is a small number of large, coalesced transfers.
2. **The bigger the `D`, the smaller the `Br/D` ratio, the worse the FA1 accounting.** That's the FA-2 motivation, and it's why "reverse the loop order" is at the top of the v2 backlog (§13).

The Nsight/roofline story on all of this lands in M9 with real measured numbers; M4 just needs the *analytical* estimate in its notes.

## 11. Correctness argument

Per §5, M4's per-tile math is `Br` **independent copies** of M3's per-row recurrence — no coupling between rows, no new algebra. So:

- If M3 is correct at `1e-5` abs tolerance, and
- If M4's kernel implements $B_r$ independent copies of that exact recurrence (no cross-row state), then

M4 is correct at the same tolerance floor. Two places bugs can enter:

- **Broadcasting `m^{\text{new}}` across `Bc`.** Row `i` uses its own running max when computing `p̃_{i,j}`. Screwing up the broadcast (e.g., accidentally using row `i'`'s max) will silently poison one row while others look fine — the exact same category of bug as forgetting the `α` rescale, and the test grid must catch it.
- **Padding on the last Q-tile or K/V-tile.** When `N % Br ≠ 0` or `N % Bc ≠ 0`, out-of-range rows/cols must contribute score `-∞` (so `p̃ = 0`) and not participate in any row-max. M3 already handles this on the KV side (`theory/M3.md` §7.6); M4 has to also handle it on the Q side. Tests include at least one non-multiple `N` case (`N = 257`) so tile-boundary bugs get exercised now, not in M7.

Tolerance for M4 kernel-vs-CPU-ref: **`< 5e-4` abs (fp32)** — the standard CUDA-vs-CPU-ref tolerance from `docs/AGENTS.md` §9. This is looser than M3's `1e-5` because M4 introduces a second axis of accumulation (the `PV` matmul across `Bc` columns) whose rounding drift is comparable to M2's naive path.

## 12. Numerical stability

Same guarantees as M3 §11, extended row-wise:

- Every $\exp$ argument in the update is $\leq 0$ (because $m^{\text{new}} \geq m$ elementwise), so $\alpha \in (0, 1]^{B_r}$ and $\tilde{P}^{(rc)} \in (0, 1]^{B_r \times B_c}$. **No overflow possible in fp32.**
- Underflow (very negative $s - m$) rounds to `0` — same failure mode as the two-pass baseline; means that term was going to be zero anyway.
- Per-row rounding error grows as $O(T_c \cdot \varepsilon_{\text{fp32}})$, same as M3.
- **Footgun:** $\ell_i$ underflow at the end still leads to $\tilde{O}_i / 0$. Same guard as M3: `O_i = (ℓ_i > 0) ? Õ_i / ℓ_i : 0`.

## 13. Deferred to v2 (M6) and later — the v2 backlog

Named up-front, so M6 has a checklist to attack and we don't accidentally do it inside M4. Every one of these becomes a bullet in `docs/flash_attention_notes.md` at end of M4:

- **`float4` vectorized loads for Q/K/V.** Scalar loads in v1; 4-wide loads cut instruction count 4× and reduce per-warp HBM transaction count.
- **Shared-memory bank conflicts** on `sK`, `sV`, `sO` (naive row-major layouts). Swizzling or +1 padding of the leading dim is the standard fix.
- **`Õ` in registers instead of shared memory.** Frees `Br·D` floats of smem; enables larger `(Br, Bc)` or higher occupancy. Requires a specific thread mapping (thread `(tx, ty)` owns `Õ[ty, d]` for `d = tx, tx+Bc, ...`).
- **Register-pressure and occupancy tuning.** Read `ptxas -v` output, tune `Br/Bc` for 2 CTAs/SM.
- **Async copies (`cp.async`).** Overlap next-tile HBM load with current-tile compute. Ampere+ (skipped on T4).
- **FA-2's loop reversal** (§6 Option B). Fixes the K/V re-read cost at large `D`.
- **`D = 128` path.** Requires opt-in to 64 KB smem or a register-resident `Õ`.
- **Multi-head / batch fan-out** in the CTA grid. Trivial in code (just `grid.y = B*H`), lands with M7 tests.
- **Tensor cores / WMMA.** Explicitly out of scope per `docs/AGENTS.md` §10; called out as future work in M10.

## 17. Understanding checkpoint (answer these out loud)

Before ticking M4 done, you should be able to answer these without notes:

1. **For your chosen `(Br, Bc, D)`, how many bytes of shared memory per CTA? How many CTAs per SM does that permit?**  On T4 at `(Br = 32, Bc = 32, D = 64)`: 37,120 B smem/CTA. T4 has 64 KB smem/SM (48 KB default per-CTA cap). One CTA per SM without opt-in, since two CTAs would need 74 KB. Threads-per-CTA (1024) also hits the max-threads-per-SM (1024) → one CTA per SM either way.

2. **What's the arithmetic intensity of your inner loop, and how does it compare to the naive kernel's?**  Per tile: FLOPs ≈ `2·Br·Bc·D` (S matmul) + `2·Br·Bc·D` (PV matmul) + `O(Br·Bc)` (softmax). HBM per tile: `2·Bc·D` floats read (K + V), amortized over `Br` rows. Arithmetic intensity per tile ≈ `4·Br·Bc·D / (2·Bc·D · 4) = Br/2` FLOP/B (fp32). Naive kernel's intensity is `O(1)` FLOP/B for the softmax stage since it mostly streams `S` and `P` through HBM. This is the roofline story we plot in M9.

3. **Where does M4 leave money on the table vs. FA-2?**  K/V re-read $T_r$ times (§10). At large `D` or small `Br`, this dominates the HBM footprint and can lose to naive on paper. FA-2 flips the loop to load K/V once and re-read Q. Named, not fixed; that's v2/v3 work.

4. **Where is the line that proves S never hits HBM?**  Point at the `sS = sQ · sK^T / √D` step (STEP 2 in §9) — its output lives in shared memory (`sS`), consumed by both `rowsum` and the `PV` matmul before the next tile overwrites it. No `cudaMalloc`, no `cudaMemcpy`, no HBM write anywhere in the block loop.

5. **What's the difference between `blockIdx.x` and `b_idx`?**  `blockIdx.x` is CUDA-provided, fixed per CTA — it selects the Q-tile. `b_idx` is a plain `int` local variable inside the kernel's `for` loop — it selects the current KV-tile. Different tiling axes, different mechanisms. (§4.1.)

## 18. Glossary

| Term | Meaning |
|---|---|
| **Q-tile** | A contiguous stripe of `Br` query rows, owned by one CTA for its entire lifetime. Selected by `blockIdx.x`. |
| **KV-tile** | A contiguous slice of `Bc` key/value columns, streamed by the CTA one at a time in a `for` loop over `b_idx`. |
| **`Br`** | Q-tile row count. M4 uses `Br = 32`. |
| **`Bc`** | KV-tile column count. M4 uses `Bc = 32`. |
| **`Tr`** | `⌈N/Br⌉` — number of Q-tiles, i.e. number of CTAs launched (per head). |
| **`Tc`** | `⌈N/Bc⌉` — number of KV-tile iterations *inside* each CTA. |
| **Per-tile state** | `(m, ℓ, Õ) ∈ ℝ^{Br} × ℝ^{Br} × ℝ^{Br × D}` — the persistent state carried across the `b_idx` loop. |
| **`α` (per row)** | `exp(m_old − m_new) ∈ (0, 1]^{Br}` — the rescale vector that keeps the running `(ℓ, Õ)` commensurable with new-block contributions after the running max updates. |
| **Option A / Option B loop order** | A: outer = Q-tile (M4 / FA-1). B: outer = KV-tile (FA-2). See §6. |
| **v2 backlog** | The `docs/flash_attention_notes.md` list of things M4 deliberately doesn't do. All of `float4`, bank-conflict fixes, register-resident `Õ`, `cp.async`, FA-2 loop reversal, `D = 128`. |
