## 1. The one-sentence goal of M5

> **Replace ad-hoc GoogleTest binaries with one Python harness that exposes every CUDA kernel through a single `flash_from_scratch` module, runs one parametrized correctness matrix, and emits one CSV row per `(variant, shape)` — so every performance claim traces to a row in `benchmarks/results/all.csv`.**

Everything else — the CUDA-event timing, the median-of-20 policy, the FLOP formula, the plot script — is *engineering* on top of that one goal.

---

## 2. Why M5 is different from M1–M4

M1–M4 each had a piece of *algorithm* to derive: softmax stability, three-kernel HBM accounting, online-softmax recurrence, tile-shape budgets. **M5 introduces no new attention math.** Instead it introduces:

- **Measurement theory** — how do you time a CUDA kernel *correctly* and what statistic do you report?
- **Analytical performance modeling** — the closed-form FLOP count, HBM-byte estimate, effective throughput, and error metrics that every row in the CSV will carry.
- **The variant-registry pattern** — one dict of callables so the benchmark loop and the correctness matrix never need editing when a new kernel lands.
- **The pybind11 shim** — deferred from M4 (`docs/AGENTS.md` §8 M3/M4 ADRs). Without it, no Python-side harness can exist.

If M1–M4 were "prove the algorithm works," M5 is "prove you can *measure* the algorithm honestly."

## 3. Measurement theory — how to time a CUDA kernel correctly

### 3.1 Why naive timing is off by orders of magnitude

A CUDA kernel launch is **asynchronous**. The host-side function `flash_fwd_v1_forward(...)` returns to Python *before* the kernel has finished — often before it has even started, because the launch just enqueues onto the default stream. Naive Python timing:

```python
t0 = time.perf_counter()
kernel(Q, K, V)            # returns immediately; kernel not done
t1 = time.perf_counter()   # measures QUEUE-LATENCY, not kernel runtime
```

This measures ~5–20 µs of launch overhead, regardless of how long the kernel actually runs. Naive fix — force the host to wait:

```python
torch.cuda.synchronize()
t0 = time.perf_counter()
kernel(Q, K, V)
torch.cuda.synchronize()   # blocks host until every stream is idle
t1 = time.perf_counter()
```

Even better — use **CUDA events**, which are timestamped *on the GPU* by the device clock (avoiding host-side clock jitter and any residual queue latency):

```python
start = torch.cuda.Event(enable_timing=True)
end   = torch.cuda.Event(enable_timing=True)
start.record()
kernel(Q, K, V)
end.record()
torch.cuda.synchronize()          # ensure `end` has actually been signaled
ms = start.elapsed_time(end)      # ms, ~0.5 µs resolution on modern GPUs
```

**Failure mode if you forget `torch.cuda.synchronize()` before reading `elapsed_time`**: `end.elapsed_time(start)` returns whatever timestamp `end` was queued at, which is before the kernel finishes — you'll get `~0.02 ms` for a 4 ms kernel. This is a specific silent failure the harness must not permit.

### 3.2 Why warm-up

The first launch of any CUDA kernel in a fresh process pays one-time costs that later launches don't:

- **CUDA context / lazy module load**: first CUDA API call in a process initializes the context (~50 ms).
- **PTX → SASS JIT** (if the module was compiled for a different arch and PTX-fallback is used — happens if a `sm_86`-compiled binary runs on a T4).
- **I-cache / constant-cache priming** on the SMs.
- **Clock ramp-up**: NVIDIA GPUs boost from base clock to boost clock after a few hundred microseconds of load (T4: 585 MHz base → 1590 MHz boost; A10G: 885 MHz → 1710 MHz). Measuring the first launch reports base-clock runtime; measuring iterations 2–20 reports boost-clock runtime — a ~2× difference.

Standard recipe (fixed for the whole project):

```
for _ in range(WARMUP_ITERS):    # 10
    kernel(...); torch.cuda.synchronize()

for _ in range(TIMED_ITERS):     # 20
    start.record(); kernel(...); end.record()
    torch.cuda.synchronize()
    samples_ms.append(start.elapsed_time(end))
```

### 3.3 Why median, not mean

CUDA runtime distributions are empirically **right-skewed** with sporadic tail spikes from:

- OS scheduler preempting the host thread mid-launch.
- Concurrent DMA (another process's memcpy sharing PCIe).
- Thermal throttling under sustained load.

The **mean** is dominated by these outliers; `mean(samples)` reports a number that is neither typical nor reproducible run-to-run. The **median** is the 50th percentile of the tightly-clustered body of the distribution — reproducible across runs to within 1–3 %.

We also record **p95** as a check on tail behavior: if `p95 / median > 1.5`, the measurement is unstable and needs `TIMED_ITERS` raised or a locked clock (deferred to M9).

Formally, given sorted samples $t_{(1)} \le t_{(2)} \le \dots \le t_{(N)}$:

$$
t_\text{med} = \begin{cases} t_{((N+1)/2)} & N \text{ odd} \\ \tfrac{1}{2}\bigl(t_{(N/2)} + t_{(N/2+1)}\bigr) & N \text{ even} \end{cases},
\qquad t_\text{p95} = t_{(\lceil 0.95 N \rceil)}.
$$

At `N=20`: median = mean of ranks 10 and 11; p95 = rank 19.

### 3.4 Coefficient of variation as a health check

Per-row sanity: define

$$
\mathrm{CV} = \frac{t_\text{p95} - t_\text{med}}{t_\text{med}}.
$$

For `N ≥ 512` on a warm GPU we expect `CV < 0.25`. Any row exceeding this is flagged in `docs/plots/` captions as "unstable timing" — the harness does not silently discard it. This is how the reader learns to trust the numbers.

## 4. The performance model — one equation per CSV column

The CSV schema (frozen for the rest of the project):

```text
variant, B, H, N, D, causal, dtype,
runtime_ms_median, runtime_ms_p95,
hbm_bytes_est, peak_alloc_bytes, tflops_effective,
max_abs_err_vs_ref, max_rel_err_vs_ref,
git_sha, gpu_name
```

Below, every math-bearing column is derived.

### 4.1 `hbm_bytes_est` — analytical HBM traffic per variant

Notation. All tensors are fp32, so element size = 4 B. Let $T = 4 \cdot B \cdot H \cdot N \cdot D$ bytes (the size of one of $Q, K, V, O$). Let $S = 4 \cdot B \cdot H \cdot N^2$ bytes (the transient `[B, H, N, N]` intermediate).

At `B = H = 1, N = 2048, D = 64, fp32`: $T = 4 \cdot 2048 \cdot 64 = 524{,}288$ bytes = **512 KB**, and $S = 4 \cdot 2048^2 = 16{,}777{,}216$ bytes = **16 MB**. All concrete numbers below use these two constants.

**Naive (M2).** Three kernels each round-trip through HBM:

$$
\text{HBM}_\text{naive} = \underbrace{2T + S}_\text{qk\_matmul} + \underbrace{2S}_\text{row\_softmax} + \underbrace{S + 2T}_\text{pv\_matmul} = 4T + 4S.
$$

Numerically: $4 \cdot 512\text{ KB} + 4 \cdot 16\text{ MB} \approx$ **66 MB**.

**Online-softmax reference (M3).** *One CTA per query row.* For each row: load Q-row once, stream K and V through in `Bc`-column tiles, write O-row once. Because CTAs are independent, each row loads its *own* copy of K and V from HBM:

- Q reads (all rows across CTAs): $T$ bytes total.
- K reads: each of the $BHN$ rows re-loads all $N$ K-columns → $B H N \cdot N D \cdot 4 = N \cdot T$ bytes.
- V reads: same as K → $N \cdot T$ bytes.
- O writes: $T$ bytes.

$$
\text{HBM}_\text{online-ref} = (2 + 2N) \cdot T \approx 2N \cdot T.
$$

At $N = 2048$: $\approx 4096 \cdot T = 4096 \cdot 512\text{ KB} \approx$ **2 GB**. This is the exact inefficiency M4 fixes — 30× worse than naive at this shape.

**Flash v1 (M4).** *One CTA per Q-tile of $B_r$ rows.* Each K-tile / V-tile is loaded once per Q-tile:

- Q reads: $T$ bytes (each tile loaded once).
- K reads: $\lceil N / B_r \rceil \cdot T$ bytes.
- V reads: $\lceil N / B_r \rceil \cdot T$ bytes.
- O writes: $T$ bytes.

$$
\text{HBM}_\text{flash-v1} = \bigl(2 + 2 \lceil N / B_r \rceil\bigr) \cdot T.
$$

At $N = 2048$, $B_r = 32$: $(2 + 2 \cdot 64) \cdot T = 130 \cdot 512\text{ KB} \approx$ **65 MB** — a ~32× reduction over online-ref, and *slightly better* than naive. FlashAttention-2's key insight (deferred to M6/beyond) is swapping the loop order so K/V are loaded once and Q is re-loaded — closing this gap further.

**Summary table** at $B = H = 1, N = 2048, D = 64, \text{fp32}$ (numbers match `benchmarks/perf_model.py`):

| Variant                | Formula                                | Bytes  |
|------------------------|----------------------------------------|-------:|
| `attention_naive`      | $(4 + 4N/D) \cdot T$                   | ~66 MB  |
| `attention_online_ref` | $(2 + 2N) \cdot T$                     | ~2 GB   |
| `flash_fwd_v1`         | $(2 + 2\lceil N/B_r \rceil) \cdot T$   | ~65 MB  |

The **story this table tells**: online-softmax alone is not enough — you must tile Q as well, or K/V re-loading dominates. Registering `attention_online_ref` in the harness makes that story a plot row, not a footnote.

### 4.2 `tflops_effective` — the standard attention FLOP count

Every performance paper uses the same convention for exact SDPA forward:

- **QK$^\top$**: for each of $B \cdot H$ heads, an $N \times D$ times $D \times N$ matmul. Standard matmul FLOP count (one multiply + one add per inner-loop step): $2 N^2 D$ per head.
- **PV**: an $N \times N$ times $N \times D$ matmul per head — another $2 N^2 D$.
- **Softmax**: $O(BHN^2)$ — for `N=2048, D=64` this is ~1600× smaller than the matmuls, so by convention ignored.

$$
\boxed{F_\text{attn} = 4 \cdot B \cdot H \cdot N^2 \cdot D}
$$

For `B=H=1, N=2048, D=64`: $F = 4 \cdot 2048^2 \cdot 64 \approx 1.07 \times 10^9$ FLOPs. Then

$$
\text{TFLOPs}_\text{eff} = \frac{F_\text{attn}}{t_\text{med} \cdot 10^{9}} \quad (\text{with } t_\text{med} \text{ in ms}).
$$

**Why "effective"** — we count the *algorithmic* FLOP budget (identical across variants), not the *actual* FLOPs executed. Flash v1 does *more* actual FLOPs than naive (some partial dot products are recomputed across CTAs), but normalizing by algorithmic work makes improvements from IO reductions show up as higher effective TFLOPs. This is the metric the M9 roofline plot needs.

### 4.3 `peak_alloc_bytes` — measured, not modeled

The harness brackets every kernel call with `reset_peak_memory_stats()`, records `baseline = memory_allocated()` *after* Q, K, V are resident, launches the kernel (which internally allocates `O` via `torch.empty_like(Q)` plus any transient intermediates), synchronizes, and records `peak = max_memory_allocated()`. The column value is $\text{peak} - \text{baseline}$.

Because $O$ is always allocated by the shim (not by the caller), $O \approx T$ bytes is included in every row:

- `attention_naive`: $\approx T + 2S$ (output + transient `S` + transient `P`).
- `attention_online_ref`: $\approx T$ (output only; no HBM transients).
- `flash_fwd_v1`: $\approx T$ (output only).
- `torch_ref`: $\approx T$ + whatever workspace PyTorch's SDPA backend needs.

Subtracting $T$ from any row gives the **transient contribution** — that's the number that grows quadratically for naive and stays flat for Flash. This column is the visual proof, per row, that "the $N \times N$ matrix never touches HBM": naive's row minus $T$ is $2S \sim N^2$; Flash's row minus $T$ is $0$.

### 4.4 `max_abs_err_vs_ref`, `max_rel_err_vs_ref` — why both

Per output element $O_{bhnd}$ compared against a reference (CPU or `torch.nn.functional.scaled_dot_product_attention`):

$$
e^\text{abs} = \max_{b,h,n,d} \bigl|O^\text{kernel}_{bhnd} - O^\text{ref}_{bhnd}\bigr|, \qquad
e^\text{rel} = \max_{b,h,n,d} \frac{\bigl|O^\text{kernel}_{bhnd} - O^\text{ref}_{bhnd}\bigr|}{|O^\text{ref}_{bhnd}| + \varepsilon}.
$$

We record both because each fails on its own:

- **Abs alone fails on large-magnitude outputs**: $O \sim 10^6 \pm 5 \times 10^{-4}$ passes a $5 \times 10^{-4}$ abs tolerance but has ridiculous relative accuracy.
- **Rel alone fails near zero**: $O \sim 10^{-8}$ vs $2 \times 10^{-8}$ has 100 % relative error but is numerically indistinguishable from noise.

`torch.allclose(a, b, atol, rtol)` uses the standard disjunction $|a - b| \le \text{atol} + \text{rtol} \cdot |b|$, so both tolerances matter. Recording both max scalars lets downstream analysis pick the appropriate regime per shape.

### 4.5 Reproducibility columns: `git_sha`, `gpu_name`

- `git_sha`: `git rev-parse --short HEAD` — pinned once per sweep. Without it, "this row is from your best commit or your worst?" is unanswerable.
- `gpu_name`: `torch.cuda.get_device_name(0)` — distinguishes T4 rows from A10G rows in a shared CSV.

## 5. The variant-registry pattern

One Python dict, one entry per kernel:

```python
# benchmarks/variants.py
@dataclass(frozen=True)
class VariantSpec:
    fn: Callable[[Tensor, Tensor, Tensor, bool], Tensor]  # (Q, K, V, causal) -> O
    supports_causal: bool
    supported_D: frozenset[int]
    supported_dtypes: frozenset[str]

VARIANTS: dict[str, VariantSpec] = {
    "torch_ref":            VariantSpec(..., True,  frozenset({32, 64, 128}), frozenset({"fp32"})),
    "attention_naive":      VariantSpec(..., True,  frozenset({32, 64}),      frozenset({"fp32"})),
    "attention_online_ref": VariantSpec(..., False, frozenset({32, 64}),      frozenset({"fp32"})),
    "flash_fwd_v1":         VariantSpec(..., False, frozenset({32, 64}),      frozenset({"fp32"})),
}
```

Every callable takes the same signature. Both the correctness harness (`tests/test_all_variants.py`) and the benchmark sweep (`benchmarks/bench_attention.py`) iterate over this dict. **Adding Flash v2 in M6 is one entry.**

`supported_D` and `supports_causal` are how the harness skips an unsupported combination cleanly — silent skips would hide bugs; explicit `pytest.skip("...")` records what was tested and what wasn't. Same in the CSV: unsupported combinations don't appear at all.

## 6. The pybind11 shim (finally lands here)

`docs/AGENTS.md` §8 M3/M4 ADRs deferred Python-side kernel access to M5. This is when it lands.

### 6.1 Layout

Per `docs/AGENTS.md` §4 (*"the pybind11 shim lives in `csrc/` beside the kernels it wraps"*):

- `csrc/bindings.cpp` — single translation unit exposing `attention_naive_forward`, `attention_online_ref_forward`, `flash_fwd_v1_forward` as pybind11 functions taking `torch::Tensor` (via `<torch/extension.h>`).
- `flash_from_scratch/__init__.py` — Python-level re-export with tensor-contract validation.
- `flash_from_scratch/_C.*.so` — the compiled extension, installed by `scikit-build-core` under `flash_from_scratch/`.

### 6.2 Tensor contract (enforced in Python)

Every entry-point validates before calling into C++:

- `dtype == torch.float32` (fp16 arrives in M8).
- `.is_cuda` and all three tensors on the same device.
- `.is_contiguous()` in the canonical `[B, H, N, D]` layout.
- `Q.shape == K.shape == V.shape`.
- `D ∈ variant.supported_D`.

Failure raises `TypeError` or `ValueError` with a message that names the field. C++-side we still `TORCH_CHECK` as a defense-in-depth (the Python side is the primary source of user-friendly errors).

### 6.3 Build backend — scikit-build-core (ADR)

`pyproject.toml` switches to `scikit-build-core` (`docs/AGENTS.md` §8 M1 already committed to hand-written pybind11 shim as opposed to `torch.utils.cpp_extension` JIT). scikit-build-core drives CMake at wheel-build time, respecting the existing `CMakeLists.txt` structure and letting `scripts/build.sh` continue to work unchanged for the C++ / GoogleTest side.

The `_C` target is guarded by `BUILD_PY_EXT=ON` so the default `scripts/build.sh` invocation (which builds `hello` and the GoogleTest binaries) is untouched.

## 7. Correctness policy — what the pytest matrix does and does not check

`tests/test_all_variants.py` parametrizes over `(variant, (B, H, N, D, causal))`:

- **Variant grid**: all four entries of the `VARIANTS` dict.
- **Shape grid (M5 slice)**: `B=H=1, N ∈ {128, 256, 512, 1024, 2048}, D ∈ {32, 64}, causal=False` — 10 shapes.
- **Total**: 4 variants × 10 shapes = **40 parametrized cases**.

Tolerance per `docs/AGENTS.md` §9:

- `torch_ref` vs CPU ref: `1e-5` abs (definition of oracle).
- CUDA fp32 kernels vs CPU ref: `5e-4` abs.
- `attention_online_ref` vs CPU ref: `1e-5` abs (algebraic equivalence).

**Deliberately out of scope of M5's grid:**

- `B > 1, H > 1` — M7.
- `causal = True` — M7.
- `D = 128` — M7.
- fp16 — M8.

The variant registry already declares which combinations each kernel supports. M7/M8 will *expand the shape grid*, not the variant list — a decoupled axis.

## 8. What we deliberately defer

- **Locked SM clock** (`nvidia-smi -lgc`) — requires root, GPU-model dependent. Modal A10G supports it; Colab T4 doesn't. Deferred to M9.
- **Process isolation** (`taskset`, `nvidia-cuda-mps`) — not needed at our shapes.
- **`torch.cuda.Graph` capture** — kernel time dominates launch overhead once `N ≥ 512`, so `torch.cuda.Event` timing is sufficient.
- **Measured HBM bytes** (via Nsight `dram__bytes.sum.per_second`) — the harness reports *analytical* HBM bytes; the Nsight cross-check lands in M9.
- **`peak_alloc_bytes` for `attention_online_ref`** — should be $0$; verified by the harness, not modeled.

## 9. Understanding checkpoint

Answer out loud before ticking M5.

1. **Why median-of-20 and not mean?** Right-skewed runtime distributions; mean is dominated by tail outliers from OS scheduling and clock throttling. Median is the 50th percentile of the tight cluster.
2. **What breaks if you forget `torch.cuda.synchronize()` before reading `elapsed_time`?** The `end` event was queued but not yet signaled — `elapsed_time` returns queue-latency time, not kernel runtime. You'll report ~10 µs for a 10 ms kernel.
3. **Why does `attention_online_ref` sit *worse* than `attention_naive` on the HBM-bytes plot at large `N`?** M3 runs one CTA per row; each CTA independently re-loads all of K and V from HBM, giving $\text{HBM} \sim 2N \cdot T$ vs naive's $\text{HBM} \sim 4T + 4S$. This is the exact inefficiency M4 fixes by grouping $B_r$ rows into one CTA.
4. **Why do we record both `git_sha` and `gpu_name` on every row?** Because "which commit / which GPU produced this number?" is the first question a reviewer asks, and it must be answerable without extra context.

## 10. Glossary

- **CUDA event** — a device-clock timestamp inserted into the stream, readable from the host after `synchronize()`.
- **Warm-up iteration** — a kernel launch whose timing is *discarded* to eliminate one-time costs (context init, PTX JIT, clock ramp-up).
- **Median-of-N** — the median of $N$ per-iteration measurements; robust to right-skewed outliers.
- **Coefficient of variation (CV)** — $(t_\text{p95} - t_\text{med}) / t_\text{med}$; a health check on timing stability.
- **Effective TFLOPs** — algorithmic FLOP count divided by measured runtime; normalizes across variants that differ in *actual* FLOPs.
- **Variant registry** — one Python dict mapping variant name → `VariantSpec`, iterated by both correctness and benchmarking.
- **Tensor contract** — the set of dtype / device / layout / shape invariants every entry-point checks before dispatching to C++.
