## 1. The one-sentence goal of M2

> **Build the "straw man" on GPU: three separate CUDA kernels that faithfully materialize `S`, `P`, and `O` in HBM — so that later, when Flash never writes `S` or `P`, the improvement is measurable rather than narrated.**

M2 does not try to be fast. Its job is to be *honestly slow*, in the exact way that Flash Attention will later demolish. Every wasted HBM byte in M2 is a byte that M4 saves. That's the whole story.

---

## 2. What M2 is *not*

Being explicit up front saves rabbit holes:

- **Not tiled.** No shared-memory blocking. That's M4.
- **Not fused.** Three separate kernel launches, three separate HBM round-trips. Fusing them is what M4 *is*.
- **Not clever.** No `float4` vectorization, no bank-conflict-free layouts, no warp shuffles for the reductions. Save it for M6.
- **Not vendor.** No cuBLAS, no cuDNN. The M1 rule ("references and baselines don't use vendor kernels") applies here too — if we called cuBLAS, we'd be measuring cuBLAS vs Flash, not naive-attention vs Flash-attention.
- **Not multi-head or multi-batch.** The MILESTONES verification grid is fixed at `B=1, H=1`. The kernel signature carries `B, H` (matches the CPU ref), but our tests won't exercise `B > 1` or `H > 1` until M7. This keeps the naive kernel small and pedagogically clean.

If you catch yourself optimizing anything in M2, stop and write it down as a note for M4/M6 instead.

## 3. Refresher: the attention we're computing

M2 introduces **zero new math** — it's the same formula from `theory/M1.md` §2:

For each `(batch, head)`, with `Q, K, V ∈ ℝ^{N × D}`:

\[
S = \frac{QK^{\top}}{\sqrt{D}}, \quad
P = \operatorname{softmax}(S), \quad
O = PV
\]

- `S ∈ ℝ^{N × N}` — pre-softmax scores.
- `P ∈ ℝ^{N × N}` — row-stochastic attention weights.
- `O ∈ ℝ^{N × D}` — final output.

Numerically stable softmax (`theory/M1.md` §4) and causal masking (`theory/M1.md` §5) work exactly the same way on GPU as they do on CPU — the math doesn't care about the hardware. What changes in M2 is *how the work is decomposed across threads*.

## 4. The three-kernel decomposition

The naive plan writes each intermediate to HBM and reads it back for the next step:

```
   HBM                        Kernel                     HBM
 ┌──────┐                 ┌──────────────┐            ┌──────┐
 │  Q   │───┐             │              │            │      │
 │  K   │───┼────────────▶│  qk_matmul   │───────────▶│  S   │
 └──────┘   │             └──────────────┘            └──────┘
                                                          │
                                                          │  read
                                                          ▼
                          ┌──────────────┐            ┌──────┐
                          │ row_softmax  │───────────▶│  P   │
                          └──────────────┘            └──────┘
                                                          │
 ┌──────┐                                                 │  read
 │  V   │────────┐                                        ▼
 └──────┘        │        ┌──────────────┐            ┌──────┐
                 └───────▶│  pv_matmul   │───────────▶│  O   │
                          └──────────────┘            └──────┘
```

Each arrow is an HBM traversal. Every arrow that goes *into* an `[N, N]` box is where the bandwidth budget dies at large `N`. Count them: **six** `N × N` traversals for the two `N × N` boxes (`S` written + read, `P` written + read, and inside `row_softmax` we effectively touch `S` and `P` back-to-back). That's the cost we'll invoice later.

**Why three kernels and not one big kernel?** Because a single GPU kernel launch can't cleanly synchronize *across* thread blocks in the middle of execution. Different blocks producing `S[i, :]` finish at different times; the softmax kernel needs *all* of `S[i, :]` for one row before it can reduce. Splitting at the synchronization boundary is the cheapest correct thing to do. Flash Attention will side-step this by rearranging the algorithm so that each block finishes its portion of `O` in isolation (no cross-block sync needed) — but that's M4.

## 5. Kernel 1 — `qk_matmul`: producing `S`

### 5.1 What it computes

For each `(b, h, i, j)`:

\[
S[b, h, i, j] = \frac{1}{\sqrt{D}} \sum_{d=0}^{D-1} Q[b, h, i, d] \cdot K[b, h, j, d]
\]

Output shape: `[B, H, N, N]`. Total elements: `B · H · N²`.

### 5.2 The naive parallelization

**One thread per output element.** Every thread owns a single `(b, h, i, j)` and computes its dot product independently:

```
tid = (blockIdx, threadIdx)  →  (b, h, i, j)
S[b, h, i, j] = 0
for d in 0..D:
    S[b, h, i, j] += Q[b, h, i, d] * K[b, h, j, d]
S[b, h, i, j] *= 1 / sqrt(D)
```

- No shared memory.
- No cooperation between threads.
- Every thread reads `2D` fp32 values from HBM and writes 1 fp32 value back.
- The scale factor `1/√D` is folded into the write so we don't need a second pass.

### 5.3 Grid & block shape

We use a 2D block over `(i, j)` inside each `(b, h)`, and a 1D grid over `b·H + h` for the `(batch, head)` axis:

```
dim3 block(16, 16);            // 256 threads/block — a round default
dim3 grid(
    (N + block.x - 1) / block.x,   // number of i-tiles
    (N + block.y - 1) / block.y,   // number of j-tiles
    B * H                          // one grid-z per (batch, head)
);
```

- **Boundary handling.** When `N` isn't a multiple of 16, the last tile has fewer valid `(i, j)` — the kernel must range-check and no-op for out-of-range threads. (The MILESTONES grid uses `N ∈ {64, 128, 512, 1024}`, all multiples of 16, but the range check is still correct hygiene.)

### 5.4 Why this is deliberately wasteful

- **Redundant loads.** Every value `Q[b, h, i, d]` is read `N` times (once per column `j`); every `K[b, h, j, d]` is read `N` times (once per row `i`). A tiled matmul would load each element into shared memory once per tile. We're not doing that in M2 — the redundancy is the point.
- **Full `S` write.** `B · H · N²` fp32 writes to HBM. At `N=4096`, that's **64 MB** just for `S`. In M4 we'll erase this line.
- **Coalescing situation.** Threads with adjacent `threadIdx.x` write adjacent `j` values → adjacent memory addresses in row-major `[N, N]` → the *write* is coalesced. The *read* of `K[j, d]` across the `d` loop is fine (contiguous in `d`); the read of `K[j, d]` across different threads with different `j` in the same warp isn't consecutive — but we don't care in M2.

## 6. Kernel 2 — `row_softmax`: turning `S` into `P`

### 6.1 What it computes

For each row `(b, h, i)`:

1. Optionally set `S[i, j] = -∞` for `j > i` (causal).
2. Compute `m = max_j S[i, j]`.
3. Compute `l = Σ_j exp(S[i, j] - m)`.
4. Emit `P[i, j] = exp(S[i, j] - m) / l`.

This is the softmax-stability trick from `theory/M1.md` §4, applied unchanged. Causal masking (§5 of M1) is applied *inside* this kernel so we don't waste a separate pass writing `-∞`s into `S`.

### 6.2 The naive parallelization

**One thread block per row.** All threads in the block cooperate on the reductions for that row:

- Grid: `(N, B · H)` — `blockIdx.x` selects the row `i`, `blockIdx.y` selects `(b, h)`.
- Block: 1D of `T` threads (e.g. 128 or 256).
- Each thread strides through the `N` scores of its row with stride `T`, so it visits `⌈N / T⌉` scores.

### 6.3 The three passes inside the kernel

Because each thread only sees a subset of the row's scores, we need **two block-level reductions** — one for the max, one for the sum — before the final element-wise write.

**Pass 1: max reduction.**
```
thread_max = -inf
for j in threadIdx.x, threadIdx.x + T, threadIdx.x + 2T, ...:
    if causal and j > i: continue     // masked positions ignored
    thread_max = max(thread_max, S[i, j])
// now block-reduce thread_max across all threads → row_max in shared mem
```

**Pass 2: sum reduction.**
```
thread_sum = 0
for j = threadIdx.x, threadIdx.x + T, ...:
    if causal and j > i: continue
    thread_sum += exp(S[i, j] - row_max)
// block-reduce → row_denom
```

**Pass 3: normalize + write.**
```
inv_denom = 1 / row_denom
for j = threadIdx.x, threadIdx.x + T, ...:
    if causal and j > i:
        P[i, j] = 0
    else:
        P[i, j] = exp(S[i, j] - row_max) * inv_denom
```

Yes, we compute `exp(S[i, j] - row_max)` twice (once in Pass 2, once in Pass 3). We *could* cache it in shared memory (needs `N` fp32 slots per block → doesn't fit for large `N`). We *could* stash it in `P` and re-normalize. In M2 we just eat the second exp — it's a leaf-level inefficiency that doesn't move the memory-bound story either way. Making this observation is more valuable than fixing it.

### 6.4 Block reduction: the CUDA idiom you need

A block reduction takes `T` values (one per thread) and collapses them to one, cooperatively. Two flavors, in order of increasing sophistication:

1. **Shared-memory tree reduction.** Each thread writes its partial value into `smem[threadIdx.x]`. Then in a loop, half the threads add their neighbor's value to their own; the stride halves each iteration. After `log₂(T)` iterations, `smem[0]` holds the reduction. `__syncthreads()` between rounds.

2. **Warp-shuffle reduction (`__shfl_down_sync`).** Faster because it stays in registers. Overkill for M2 — the tree reduction is fine.

We'll use the tree reduction. It's the same pattern for max and sum; only the reducer op changes.

### 6.5 Why row-per-block

- Each row is independent — no cross-row synchronization.
- One row of `N` fp32 values is `4N` bytes, easily reduced by a single block.
- Number of blocks = `B · H · N` — plenty of parallelism (e.g. `B=1, H=1, N=1024` gives 1024 blocks, saturating 40 SMs on T4).
- Alternatives (like one thread per row, or one warp per row) exist and are legitimate — but "block per row" gives us the cleanest reduction and is the textbook choice for this pattern.

### 6.6 HBM cost

Reads `S` once and writes `P` once — both `[B, H, N, N]`. That's `2 · B · H · N²` fp32 elements = `8 · B · H · N²` bytes. For `N=4096, B=1, H=1`: **128 MB moved per launch, ~all reads and writes**. Almost no useful compute — a pure streaming kernel with arithmetic intensity ≈ 1 exp + 1 mul per 4 bytes read, or roughly `0.5 FLOP/byte`. This is the kernel most likely to sit *closest* to the HBM bandwidth wall (see §10).

## 7. Kernel 3 — `pv_matmul`: producing `O`

### 7.1 What it computes

For each `(b, h, i, d)`:

\[
O[b, h, i, d] = \sum_{j=0}^{N-1} P[b, h, i, j] \cdot V[b, h, j, d]
\]

Output shape: `[B, H, N, D]`. Total elements: `B · H · N · D`.

### 7.2 The naive parallelization

Same shape as `qk_matmul` but with the "inner" axis being `j ∈ [0, N)` instead of `d ∈ [0, D)`, and the "output" axes being `(i, d)` instead of `(i, j)`:

```
tid → (b, h, i, d)
O[b, h, i, d] = 0
for j in 0..N:
    O[b, h, i, d] += P[b, h, i, j] * V[b, h, j, d]
```

- Grid: `((N + 15) / 16, (D + 15) / 16, B * H)`.
- Block: `(16, 16, 1)` over `(i, d)`.
- One thread per output element.

### 7.3 HBM cost

- Reads `P`: `N²` fp32 elements per `(b, h)`.
- Reads `V`: `N · D` fp32 elements per `(b, h)`.
- Writes `O`: `N · D` fp32 elements per `(b, h)`.

For `N ≫ D`, this is dominated by the `N²` read of `P`.

## 8. Just-enough CUDA for M2

If §5–§7 already made sense, skip to §9. Otherwise, this section is a minimal primer to unblock the implementation.

### 8.1 The launch: `kernel<<<grid, block>>>(args...)`

- `grid` and `block` are 3D `dim3` structs. Any unset dim defaults to 1.
- Total threads = `grid.x * grid.y * grid.z * block.x * block.y * block.z`.
- Every thread runs the same kernel code, but sees different `blockIdx` and `threadIdx`.

### 8.2 Indexing

Standard idiom for mapping a 2D thread block to an `(i, j)` output element:

```cpp
int i = blockIdx.y * blockDim.y + threadIdx.y;
int j = blockIdx.x * blockDim.x + threadIdx.x;
if (i >= N || j >= N) return;   // boundary guard
```

Standard idiom for mapping the "batch × head" grid-z:

```cpp
int bh = blockIdx.z;   // in range [0, B*H)
int b  = bh / H;
int h  = bh % H;
```

### 8.3 HBM ≠ shared memory ≠ registers

Three levels of memory, ordered by speed (fast to slow):

- **Registers.** Per-thread. ~1 cycle access. Automatic in C++ — every local variable that fits.
- **Shared memory.** Per-block, on-chip. ~30 cycles. Declared with `__shared__ float smem[...]`. **We don't use it in M2** — that's the whole naive premise.
- **Global memory (HBM).** Off-chip, accessed via the memory controller. ~400 cycles per uncached miss, but coalesced accesses hide latency well. Every `Q[...]`, `K[...]`, `V[...]`, `S[...]`, `P[...]`, `O[...]` in M2 lives here.

The HBM byte accounting in §9 is counting the traffic between the SMs and this off-chip memory.

### 8.4 Coalesced access, in one sentence

If 32 threads in a warp read 32 consecutive 4-byte addresses on the same cycle, the hardware combines them into **one** 128-byte transaction. Uncoalesced access can require up to 32 transactions for the same data — a 32× bandwidth hit. Our `[B, H, N, D]` layout was chosen (see `docs/AGENTS.md` §5.1) so that walking `d` inside a warp coalesces. In M2, our `qk_matmul` writes coalesce (threads with adjacent `threadIdx.x` write adjacent `j` values); the reads of `K` are less coalesced but we don't fix it.

### 8.5 `cudaMalloc` / `cudaMemcpy` / `cudaFree`

Every CUDA program allocates device memory with `cudaMalloc`, copies data in with `cudaMemcpy(..., cudaMemcpyHostToDevice)`, runs kernels, copies results back, and frees with `cudaFree`. Our launch wrapper hides all of this from callers. Standard error-check pattern (already used in `csrc/hello.cu`):

```cpp
static void check(cudaError_t err, const char* where) {
    if (err != cudaSuccess) {
        fprintf(stderr, "CUDA error at %s: %s\n", where, cudaGetErrorString(err));
        exit(1);
    }
}
```

### 8.6 `cudaDeviceSynchronize()`

Kernel launches are asynchronous. Call `cudaDeviceSynchronize()` before reading results back or before timing, or you'll see stale/undefined data. Every M2 test synchronizes right before diffing against the CPU ref.

## 9. HBM byte accounting: the theoretical heart of M2

This is the analysis that `docs/memory_analysis.md` (rough draft in M2, finalized in M9) has to make concrete.

### 9.1 The formula

For `B=1, H=1`, fp32 (4 B/element):

| Kernel        | Reads (elements)       | Writes (elements) | Bytes touched |
|---------------|------------------------|-------------------|---------------|
| `qk_matmul`   | `2 · N · D` (Q, K)     | `N²` (S)          | `4 · (2ND + N²)` |
| `row_softmax` | `N²` (S)               | `N²` (P)          | `4 · (2N²)` |
| `pv_matmul`   | `N² + N · D` (P, V)    | `N · D` (O)       | `4 · (N² + 2ND)` |
| **Total**     | —                      | —                 | **`4 · (4ND + 4N²)`** |

For `N ≫ D` (which is the interesting regime), the `4N²` term dominates. Concrete numbers:

| `N`   | `S` size | Naive total HBM traffic (D=64) |
|-------|----------|-------------------------------|
| 128   | 64 KB    | 464 KB    |
| 256   | 256 KB   | 1.31 MB   |
| 512   | 1.0 MB   | 4.5 MB    |
| 1024  | 4.0 MB   | 17 MB     |
| 2048  | 16 MB    | 67 MB     |
| 4096  | 64 MB    | 268 MB    |

### 9.2 What "quadratic in N" means in practice

- Double `N` → memory traffic **4×**.
- Sequence lengths in real transformer training (8k, 32k, 128k context) would demand tens of GB *per attention layer*. This is why long-context training was infeasible before Flash Attention.
- The Flash Attention v1 forward kernel (M4) touches ≈ `4 · (2ND + 2ND + ND) = 20ND` bytes per `(b, h)` — **linear in N** for fixed `D`. That's the qualitative difference we're setting up.

### 9.3 Peak transient allocation

`benchmarks/results/naive_memory.csv` logs the actual `cudaMalloc` sizes required:

- `S`: `4 · N²` bytes.
- `P`: `4 · N²` bytes.
- (`Q`, `K`, `V`, `O` are caller-provided — we don't count them.)

At `N=4096`, that's **128 MB of transient device memory** for one attention layer on one `(b, h)` pair. A 40-layer transformer would need 5.1 GB *just for the naive scratch buffers* — before parameters, activations, or gradients.

### 9.4 The claim we're setting up for M4

> "Flash Attention v1 forward computes exact attention with `< 5%` of the HBM traffic that the naive kernel uses at `N ≥ 1024`."

Every number in that claim traces back to a row in `naive_memory.csv` and a corresponding row in the M4 harness. Publishing the M2 CSV honestly now is how we earn the right to state that number later.

## 10. Why the naive path is memory-bound

### 10.1 Arithmetic intensity, in one paragraph

**Arithmetic intensity** is `FLOPs performed / bytes moved`. It measures how much work you do per unit of memory traffic — higher is better for compute-bound kernels, lower for memory-bound.

- `qk_matmul`: `2ND` FLOPs per output element (D multiplies + D adds), and it writes 1 output element for every `2D + 1` HBM elements touched. Per byte: `2ND / (4 · (2ND + N²)) ≈ 1 / (2 · (1 + N/(2D)))`. For `N=4096, D=64`: **≈ 0.03 FLOP/byte**. Very low.
- `row_softmax`: ~3 FLOPs per input element (subtract, exp, multiply), plus one comparison. Per byte: `3N² / (4 · 2N²) ≈ 0.375 FLOP/byte`. Also very low.
- `pv_matmul`: `2N` FLOPs per output. Per byte: `2N · N · D / (4 · (N² + 2ND)) ≈ 2ND / (4 · (2D + N))`. For `N=4096, D=64`: **≈ 0.5 FLOP/byte**.

### 10.2 The ridge point

Every GPU has a "ridge point" — the arithmetic intensity where compute peak = memory peak. For Colab T4:

- Peak fp32 ≈ 8.1 TFLOP/s.
- Peak HBM ≈ 320 GB/s.
- **Ridge ≈ 8100 / 320 ≈ 25 FLOP/byte.**

Every naive M2 kernel has arithmetic intensity well below 1 FLOP/byte — that's **two orders of magnitude below the ridge**. The kernel spends nearly all its wall-clock time waiting on HBM. Adding more FLOPs (bigger `D`, more work per element) would be free until we approach the ridge. That's the "memory-bound" diagnosis.

### 10.3 Lower bound on runtime

For `N=4096, D=64, B=H=1`: 268 MB of HBM traffic ÷ 320 GB/s ≈ **0.84 ms** just to move the bytes, before any FLOPs happen. Any actual measured runtime *slower* than this is fine (we might not be saturating bandwidth); any runtime *faster* would be a bug (we're not moving the bytes we claim to). This is how we'll sanity-check the M9 Nsight report against the analytical prediction.

## 11. Correctness: the CPU ref becomes the judge

The correctness chain from `theory/M1.md` §8 now activates its next link:

```
        C++ CPU ref (fp64 math, from M1)
                    ⇕  ← new in M2; abs tol 1e-4
        Naive CUDA kernel (fp32)
```

### 11.1 What we test

Direct C++ GoogleTest under `tests/cpp/test_attention_naive.cu`, calling `attention_naive_forward(...)` and diffing element-wise against `attention_cpu_ref<float>(...)` on the exact same random inputs. Grid (from MILESTONES verification plan):

- `B = 1, H = 1`.
- `N ∈ {64, 128, 512, 1024}` — 4 values.
- `D ∈ {32, 64}` — 2 values.
- `causal ∈ {false, true}` — 2 values.
- Total: **16 parametrized cases**, plus a handful of edge-case tests (N=1, uniform inputs, single-block corner).

### 11.2 The tolerance

`docs/AGENTS.md` §9 pins the rule: CUDA-fp32-vs-CPU-ref tolerance is **`5e-4` abs**. MILESTONES §M2 mentions "~1e-4" — we use `5e-4` (the AGENTS value) so we don't set a tighter bar than the project-wide policy. The C++ ref computes in fp64 internally, so this tolerance is measuring *the GPU kernel's fp32 accumulation drift*, not the reference's error.

### 11.3 Why no Python test in M2

`tests/reference.py` is fp32 NumPy, and calling a `.cu` symbol from Python would require pybind11 — deferred to M4 by `docs/AGENTS.md` §8. GoogleTest calls the kernel directly from a `.cu` test binary that `#include`s `attention_cpu_ref.hpp`. No shim, no binding, no throwaway code.

## 12. What we're going to build (artifact by artifact)

Six artifacts. Total code ≈ 400 lines including tests.

### 12.1 `csrc/attention_naive.cu` — the three kernels + launch wrapper

Contains:

- `__global__ void qk_matmul_kernel(...)`
- `__global__ void row_softmax_kernel(...)` (with `is_causal` template param or bool arg)
- `__global__ void pv_matmul_kernel(...)`
- `void attention_naive_forward(const float* Q_d, const float* K_d, const float* V_d, float* O_d, int B, int H, int N, int D, bool is_causal, cudaStream_t stream = 0)` — the host-side launch wrapper. Allocates transient `S` and `P` device buffers, launches the three kernels in order, frees the buffers.
- One overload that takes host pointers, allocates all six device buffers, memcpys, launches, memcpys back, and frees — for convenience in tests.

Function signature mirrors `attention_cpu_ref` (same argument order + `is_causal`).

### 12.2 `CMakeLists.txt` (edit) — build the new target

- Add `attention_naive.cu` guarded by `HAVE_CUDA`.
- Add a new GoogleTest target `test_attention_naive` that links against both `attention_cpu_ref` (INTERFACE lib) and the compiled `attention_naive.cu`.
- Register with `gtest_discover_tests`.

### 12.3 `tests/cpp/test_attention_naive.cu` — the correctness gate

- Parametrized GoogleTest over `(N, D, causal)` on the M2 verification grid.
- Uses the same `std::mt19937` seeded RNG as the M1 CPU-ref test.
- Passes `float` host pointers to `attention_naive_forward` (host-pointer overload) → device does its work → results diffed against `attention_cpu_ref<float>` on the same inputs.
- Edge-case tests: `N=1` (should give `O = V`), causal-first-row-equals-V[0], uniform-Q gives uniform attention → mean of V.
- Tolerance: `5e-4` absolute (per `docs/AGENTS.md` §9).

### 12.4 `benchmarks/naive_memory.py` — the CSV logger

Not a benchmark (that's M5). A tiny script that, for each `N ∈ {128, 256, 512, 1024, 2048, 4096}`:

1. Computes analytical peak transient bytes (`4 · N² · 2` for S and P).
2. Computes total HBM traffic (from §9.1).
3. Writes one row to `benchmarks/results/naive_memory.csv`.

Analytical-only in M2 — no GPU needed to run this, so it works on the Mac-local box. (Actual measured HBM traffic waits for M9's Nsight profile.) Columns:

```
N, D, S_bytes, P_bytes, transient_bytes_total, hbm_traffic_bytes_analytical
```

## 13. Build order

Same principle as M1: every step has an immediate correctness check attached.

1. **`csrc/attention_naive.cu` — `qk_matmul_kernel` first.**
   Build it, then temporarily wire a `test_qk_only` test that computes `S = QKᵀ/√D` on GPU and diffs against a CPU-side triple-loop matmul. Green here = matmul indexing is right.

2. **Add `row_softmax_kernel`.**
   Add a `test_row_softmax_only` test that feeds a known `S` (e.g. one row = `[0, 0, 0, ..., 0]` → softmax should be uniform `1/N`) and checks the output. Green here = block reduction is right.

3. **Add `pv_matmul_kernel`.**
   Same drill — small dedicated test with a known `P` (identity) → `O` should equal `V`.

4. **Wire the launch wrapper `attention_naive_forward`.**
   Now run the full parametrized test grid from §12.3. This is the M2 gate.

5. **CSV + plot + memory analysis prose.**
   Pure post-hoc analysis, no GPU. Can be written concurrently with any of the above.

Each step keeps the diff to under ~80 lines of code, so if something breaks you know exactly where.

## 14. Understanding checkpoint (answer these out loud)

Before ticking M2 done, you should be able to answer these without notes:

1. **The strawman thesis.** *At `N=4096, D=64, fp32`, how many bytes does `S` alone occupy on HBM? What fraction of Colab T4's 64 KB shared-memory-per-SM budget is that?*
   `4 · 4096² = 64 MB`. 64 MB / 64 KB ≈ **1000×** the SM's shared-memory budget. `S` fundamentally can't live anywhere except HBM in this design.

2. **Which kernel dominates.** *For large `N`, which of the three kernels do you predict eats the most wall-clock time, and why?*
   Predicted answer: `qk_matmul` and `row_softmax` are neck-and-neck for the top spot — they both touch `O(N²)` HBM bytes with very low arithmetic intensity. `pv_matmul` is third because it does more useful FLOPs per byte moved. To be verified with Nsight in M9.

3. **Why not just one big kernel.** *Why can't we fuse the three kernels into one to save the HBM round-trips?*
   Because `row_softmax` for row `i` needs *all* of `S[i, :]`, and different thread blocks producing `S[i, :]` finish at different times — inter-block synchronization inside a single kernel launch isn't possible on CUDA. Flash's answer is to *not need* the full row: it computes the softmax incrementally over K/V tiles, which lets everything for one output tile fit inside one block.

4. **What "memory-bound" means numerically.** *Compute the arithmetic intensity of `row_softmax`. Given Colab T4's ridge of ~25 FLOP/byte, where does this kernel sit relative to the ridge?*
   Roughly `0.375 FLOP/byte` (see §10.1) — about **65× below the ridge**. Deeply memory-bound. Doubling the compute would be free; halving the HBM traffic would ~double the speed.

5. **Correctness link.** *Why diff against the C++ CPU ref (`attention_cpu_ref.hpp`) and not against `tests/reference.py` (the NumPy mirror)?*
   The C++ ref is what a `.cu` test binary can `#include` directly, no bindings. The NumPy mirror is validated *against PyTorch* in M1, and the C++ ref is validated against the NumPy mirror by construction — so diffing the CUDA kernel against the C++ ref transitively closes the chain back to PyTorch.

6. **Causal + reductions.** *When causal is on, do you need special handling inside the softmax reductions to avoid `-inf` polluting the sum?*
   No, `-inf` handles itself: `max(-inf, x) = x`, `-inf - m = -inf`, `exp(-inf) = 0`. The masked positions contribute zero to both max and sum. The **only** care needed is on the final normalization write: for masked positions (`j > i`) we must write `P[i, j] = 0` explicitly (not `exp(-inf) / l = 0/l`), so downstream `pv_matmul` reads exact zeros. Either write `0` or write the `exp` result and rely on IEEE — pick one and be consistent.

## 15. Glossary

| Term | Meaning |
|---|---|
| **HBM** | High-Bandwidth Memory — the off-chip DRAM on the GPU package. Colab T4: 320 GB/s peak. This is what the "memory-bound" story is measured against. |
| **Shared memory** | Per-block on-chip scratchpad. ~30 cycles vs HBM's ~400 cycles. **Not used in M2** — we're being naive on purpose. |
| **Kernel** | A GPU function marked `__global__`, launched with `<<<grid, block>>>` syntax. Each of `qk_matmul`, `row_softmax`, `pv_matmul` is one kernel. |
| **Thread block** | A group of threads that share on-chip resources and can synchronize with `__syncthreads()`. Also called a CTA (cooperative thread array). |
| **Grid** | A collection of blocks. All blocks in the grid run the same kernel; they can't synchronize with each other mid-kernel. |
| **Warp** | 32 threads that execute in lockstep on one SM. The unit of scheduling. Coalescing works at warp granularity. |
| **Coalesced access** | When 32 threads of a warp read 32 consecutive 4-byte addresses, the hardware combines them into one 128-byte transaction. Uncoalesced = up to 32× more transactions. |
| **HBM byte accounting** | Counting reads + writes to global memory to predict the memory-bandwidth-limited runtime of a kernel. |
| **Arithmetic intensity** | `FLOPs / bytes-moved`. Lower = memory-bound; higher = compute-bound. Ridge point separates the two regimes. |
| **Ridge point** | Arithmetic intensity at which compute peak equals memory peak for a given GPU. ~25 FLOP/byte on Colab T4 fp32. |
| **Memory-bound** | Kernel whose runtime is limited by HBM bandwidth rather than compute throughput. Every M2 kernel is memory-bound. |
| **Block reduction** | Collapsing `T` per-thread values into one, using shared memory (tree reduction) or warp shuffles. Used by `row_softmax` for row-max and row-sum. |
| **`__syncthreads()`** | Barrier: all threads in a block wait until all reach this line. Used between rounds of a shared-memory reduction. |
| **Transient allocation** | Intermediate device buffers (`S` and `P`) that exist only during one attention forward pass. Peak transient bytes = the metric M2 CSV logs. |
| **`cudaMemcpy` / `cudaMalloc`** | Standard CUDA host-side APIs for moving data to/from device and allocating device memory. |
| **Straw man** | An intentionally weak baseline whose main job is to make the improvement measurable. M2 is the straw man for M4. |
