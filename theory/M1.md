## 1. The one-sentence goal of M1

> **Define what "correct" means, before writing a single line of CUDA.**

M1 doesn't ship a GPU kernel. It ships an **oracle** — a slow, painfully readable implementation of attention that every future CUDA kernel will be compared against. If M1 is wrong, every downstream milestone is wrong. If M1 is right, every future performance claim in this repo rests on a solid foundation.

---

## 2. What is attention, actually?

Attention takes three tensors — `Q` (queries), `K` (keys), `V` (values) — each shaped `[B, H, N, D]`, and produces an output `O` of the same shape.

Symbols (from `docs/AGENTS.md` §5.1):

- `B` = batch size (how many independent sequences)
- `H` = number of heads (parallel attention "channels")
- `N` = sequence length (tokens per sequence)
- `D` = head dimension (features per token per head)

For **one** batch entry and **one** head, ignore `B` and `H` — you're just working with three `[N, D]` matrices. Then attention is these three steps:

### Step 1 — Similarity: how much does each query care about each key?

\[
S = \frac{Q K^{\top}}{\sqrt{D}}
\]

- Shape of `S`: `[N, N]`.
- `S[i, j]` is a single number: "the score of query row `i` against key row `j`."
- Bigger `S[i, j]` = query `i` cares more about key `j`.

This is the `NxN` matrix that Flash Attention (M4+) refuses to write to HBM. But in M1, we happily write it out — the whole point is readability.

### Step 2 — Normalize: turn scores into probabilities (per row)

\[
P = \text{softmax}(S) \quad\text{(applied to each row separately)}
\]

- Shape of `P`: `[N, N]`.
- Each row of `P` sums to 1.0 and is non-negative → it's a probability distribution over the `N` key positions.
- `P[i, :]` is "the attention distribution of query `i` over all keys."

### Step 3 — Mix: use the probabilities to blend the values

\[
O = P V
\]

- Shape of `O`: `[N, D]`.
- `O[i]` is a weighted average of the value rows, using row `i` of `P` as weights.

**Intuition.** For each query token `i`, look at every other token, decide how relevant it is (that's `S[i, :]`), turn those into weights (that's `P[i, :]`), and produce your output as a weighted mix of the values (`O[i]`).

Then repeat this whole thing independently for every `(batch, head)` pair. That's it — that's the whole formula.

---

## 3. Why divide by √D?

If entries of `Q[i]` and `K[j]` are ~unit-variance, then their dot product (a sum of `D` products) has variance ≈ `D`, i.e. **std ≈ √D**. Without scaling, scores grow with head dim and blow up inside `exp(·)`:

- `D = 64` → scores ~±10, `exp(10) ≈ 22000`. Borderline.
- `D = 128` → scores ~±20, `exp(20) ≈ 5 × 10⁸`. Softmax saturates (near one-hot) → gradients vanish.

Dividing by `√D` cancels the variance growth so pre-softmax scores stay ~unit-variance regardless of head dim.

**Takeaway.** Hardcode `1/√D`. Get it wrong by a constant and every future kernel is silently off by that same constant.

## 4. The softmax stability trick (the heart of M1)

This is the single most important idea in M1. It also seeds the entire online-softmax recurrence used by Flash Attention in M3+.

### The naive formula

Softmax on a row `x = [x_0, x_1, ..., x_{N-1}]`:

\[
\text{softmax}(x)_j = \frac{e^{x_j}}{\sum_k e^{x_k}}
\]

### Why the naive formula breaks

`float32` can only hold numbers up to about `3.4 × 10³⁸`. But:

- `exp(100) ≈ 2.7 × 10⁴³` → **overflow to `+inf`**.
- Then both numerator and denominator are `inf`, giving `inf/inf = NaN`.
- Your entire output is garbage from that point on.

Even without full overflow, `exp(50)` = `5.2 × 10²¹`, which is representable but produces catastrophic loss of precision when summed with smaller terms.

### The fix — subtract the row max

Let `m = max_j(x_j)`. Then:

\[
\text{softmax}(x)_j = \frac{e^{x_j - m}}{\sum_k e^{x_k - m}}
\]

This is **exactly equal** to the naive formula — you're multiplying top and bottom by `e^{-m}`, which cancels. But numerically, everything is safe:

- `x_j - m ≤ 0`, so `e^{x_j - m} ∈ (0, 1]`. No overflow.
- The largest exponent is `e^{m - m} = e^0 = 1`, contributing at least one `1` to the sum. So the denominator is always ≥ 1 → no division by zero.
- The smallest exponent might underflow to 0 (if `x_j - m` is very negative), but that just means the corresponding weight is negligibly small — which is the right answer.

### Concrete example

Take `x = [100, 100, 100]`.

- **Naive:** `exp(100) / (3 · exp(100))` → `inf / inf` → `NaN`. ✗
- **Shifted:** `m = 100`, so `x - m = [0, 0, 0]`, softmax = `[1/3, 1/3, 1/3]`. ✓

Same answer mathematically, but only the shifted version survives fp32.

### Why this matters beyond M1

Flash Attention sees `x` one **block** at a time — it can't compute `max_j(x_j)` in one shot. Instead it maintains a **running max `m`** and **running sum `l`** and rescales as new blocks arrive. That online recurrence (M3) is a direct generalization of this shift trick — so understanding *why* the shift preserves the answer is what makes M3 land.

## 5. Causal masking, explained slowly

### The problem it solves

In language models (GPT-style), when the model is generating token `i`, it should only look at tokens `0, 1, ..., i` — **not** at future tokens `i+1, ..., N-1`. Otherwise the model is "cheating" — peeking at the answer during training.

"Causal" is the ML word for "no peeking into the future."

### The mathematical fix

**Before** the softmax step, set:

\[
S[i, j] = -\infty \quad \text{for all } j > i
\]

That is: zero out the strict upper triangle of `S` by setting it to `-inf`. Why `-inf`?

- `exp(-inf) = 0` in IEEE floating point.
- So masked positions contribute **zero** to both the numerator and denominator of softmax.
- Their weight in `P` is exactly 0, so they contribute nothing to `O`.

### Why not `0` or `-1e9`?

- **Setting to `0`.** Wrong — softmax(0) is not zero, it's some positive weight. That's still peeking.
- **Setting to `-1e9`.** Almost equivalent to `-inf` in practice (`exp(-1e9)` underflows to `0`), and it dodges any weirdness with `inf` arithmetic. Some codebases prefer this. For M1's reference, either is fine — pick one and be consistent.

### Does causal + stability play nicely?

Yes, and it's worth understanding why:

- After masking, `S[i, j] = -inf` for `j > i`.
- Row max `m_i = max_j(S[i, j])` — since we're taking a max, `-inf` entries are automatically ignored.
- After subtracting max: `S[i, j] - m_i = -inf` for masked positions (`-inf - anything = -inf`).
- `exp(-inf) = 0` → masked positions correctly get zero weight.

No extra bookkeeping. The two tricks compose perfectly.

### How you'll implement it

Just a bool flag:

```
if causal and j > i:
    S[i, j] = -inf
```

That's it. One line, threaded through both the C++ header and the NumPy mirror.

## 6. Why the CPU reference must not use BLAS/cuDNN

Our correctness story is a chain:

```
CUDA kernel → matches → C++ CPU ref → matches → NumPy ref → matches → PyTorch SDPA
```

For this chain to catch bugs, **each link must fail independently**. If your reference internally calls `cblas_sgemm` and PyTorch also uses BLAS under the hood, they'll agree even when both are wrong — a **tautology test**, worse than no test because it gives false confidence.

### The rule

The reference is **stupid, slow, and readable**:

- Three nested `for` loops for the matmul.
- Explicit softmax with a visible `-max` shift.
- Explicit causal mask as an `if`.
- No `cblas_*`, `cuBLAS`, or `torch.matmul` inside the reference.

It runs on `N ≤ 32` — milliseconds either way. Slow-and-obvious beats fast-and-clever for a reference.

### Precision: run the reference in `float64`

Even when inputs come in as fp32, the reference computes in `float64` internally:

- fp64 ≈ 15 decimal digits of precision; fp32 ≈ 7.
- Reference rounding error is ~10⁻¹⁶ per op vs ~10⁻⁷ for fp32 → **effectively exact from fp32's perspective**.

So when a fp32 CUDA kernel disagrees with the reference, the error is the kernel's, not the reference's.

## 7. The `[B, H, N, D]` layout, in plain English

Row-major `[B, H, N, D]` means the **last dim (`D`) varies fastest** in memory: for a query row `Q[b, h, i, :]`, the `D` elements sit at consecutive addresses; strides for the outer dims are `D`, `N·D`, `H·N·D`.

**Why this order (foreshadowing M4+).** A GPU warp (32 threads) reading `Q[b, h, i, 0..31]` hits consecutive addresses → coalesced into one memory transaction, ~an order of magnitude faster than scattered access. `[B, N, H, D]` would scatter heads for the same token and lose that.

M1 doesn't touch a GPU, but the reference accepts `[B, H, N, D]` inputs and loops over `(b, h)` on the outside — so no shape refactor is needed in M2+.

## 8. The correctness chain: how we trust our GPU code later

Here's the full picture of what M1 sets up:

```
       (M1 — this milestone)
       ┌─────────────────────────────────────┐
       │   NumPy ref (float64)               │
       │   ⇕ compared in tests               │
       │   torch.nn.functional.SDPA (float32)│
       └─────────────────────────────────────┘
                    ⇕ (by construction: same algorithm, same order)
       ┌─────────────────────────────────────┐
       │   C++ header ref (templated)        │
       └─────────────────────────────────────┘
                    ⇕ (M2+ CUDA tests will assert this)
       ┌─────────────────────────────────────┐
       │   Every future CUDA kernel          │
       │   (naive, online, flash-v1, ...)    │
       └─────────────────────────────────────┘
```

### What each link tells you

- **NumPy ↔ PyTorch:** these are two *totally independent* implementations of the same math. If they agree to 1e-5, it's genuinely unlikely both are wrong in the same way. This is the **strongest link** in the chain.
- **NumPy ↔ C++ header:** these are the *same algorithm* written in two languages. They agree by construction. Not a strong cross-check — but that's fine, because NumPy is already validated against PyTorch.
- **C++ header ↔ CUDA kernels:** this is the whole point of the reference — it's what every CUDA kernel gets diffed against, in M2 and beyond.

**Why keep both the C++ header and the NumPy ref?** CUDA test binaries are C++ — they `#include "attention_cpu_ref.hpp"` directly. Calling Python from a CUDA test binary is possible but ugly. Each ref is ~50 lines, so having both costs almost nothing.

## 9. What we're going to build (artifact by artifact)

Four small files. Total code ≈ 200 lines.

### 9.1 `csrc/attention_cpu_ref.hpp` — the C++ oracle

- **Header-only.** No `.cpp`, no linker step. Just `#include` and use.
- **Templated on `T`** (`float`, `double`). One implementation serves fp32 and fp64.
- **Three nested loops** for `QK^T`. Three nested loops for `PV`. No BLAS.
- **Numerically stable softmax** (subtract row max).
- **Causal as a bool parameter.** One `if` inside the score loop.

Signature will look like (pseudocode, not to write yet):

```
template<typename T>
void attention_cpu_ref(
    const T* Q, const T* K, const T* V, T* O,
    int B, int H, int N, int D, bool causal
);
```

### 9.2 `tests/reference.py` — the NumPy mirror

- Pure NumPy, casts inputs to `float64` internally regardless of input dtype.
- Same algorithm as the C++ header.
- One function: `attention_reference(Q, K, V, causal) -> O`.

**Style decision.** Explicit `for` loops for the matmul (strict, guaranteed no BLAS) vs `np.einsum`/`@` (pragmatic). At `N ≤ 32` both are milliseconds — prefer strict to eliminate any tautology-test risk.

### 9.3 `tests/util_tensors.py` — the fixed-seed tensor generator

- One function: `make_qkv(B, H, N, D, dtype, seed=0) → (Q, K, V)`.
- Uses a fixed-seed generator so every test in the project gets the same numbers.
- Small file, but load-bearing — every downstream milestone imports it.

Why it deserves its own file (instead of inlining into each test):

- If we later change RNG (e.g. `torch.randn` → `torch.randn(generator=...)`), one edit updates all tests.
- Ensures M2's CUDA kernel and M1's ref are compared on the *exact same* `(Q, K, V)`.

### 9.4 `tests/test_reference_matches_torch.py` — the actual gate

This is the file that must be green for M1 to be "done." It:

1. Loops over `N ∈ {8, 16, 32}`, `D ∈ {8, 16, 32}`, `causal ∈ {False, True}` — that's **18 test cases**.
2. Generates `(Q, K, V)` in fp32 via `util_tensors.make_qkv(...)`.
3. Computes `O_ref` via our NumPy reference (float64 internally, cast back to fp32).
4. Computes `O_torch` via `torch.nn.functional.scaled_dot_product_attention(..., is_causal=causal)` on CPU.
5. Asserts `max(abs(O_ref - O_torch)) < 1e-5`.

That's the whole gate. If this is green, the oracle is trustworthy and we can move on to M2.

The tolerance `1e-5` is pinned in `docs/AGENTS.md` §9 — the "CPU ref vs PyTorch, fp32" regime.

## 10. The shape grid: why so small?

M1 tests use `N ∈ {8, 16, 32}` and `D ∈ {8, 16, 32}`. Why not `N=1024` or bigger?

- **Speed.** The NumPy reference is `O(N²D)` with slow Python loops. `N=32, D=32` runs in <1 ms. `N=1024` would take seconds — unacceptable for CI, which will run these tests forever.
- **Bug coverage.** Off-by-one errors in the mask, transposition bugs in `Q @ K.T`, softmax stability bugs, causal indexing bugs — all show up just as clearly at `N=8` as at `N=8192`. Big sizes buy nothing for correctness at this stage.
- **Division of labor.** Big-`N` correctness testing lives in M2+, where the CUDA kernels handle it efficiently.

The `causal ∈ {False, True}` axis is separate because it's a **different code path**. Testing only one would leave the mask branch untested.

**Bottom line:** small shapes, complete coverage, fast tests. That's the M1 sweet spot.

## 11. Open decisions that touch M1

`docs/AGENTS.md` §8 flags two decisions with deadline "confirm before M4":

- **Python binding style** — pybind11 vs `torch.utils.cpp_extension`.
- **C++/CUDA test framework** — pytest-via-binding vs GoogleTest.

Neither blocks M1. Our M1 test compares the NumPy mirror to PyTorch; the C++ header is validated transitively (same algorithm as NumPy) and gets a direct workout in M2 when the naive CUDA kernel is compared against it. **Defer both to M4.**

## 12. Build order

Here's the order that lets each artifact *check its own correctness* as you write it:

1. **`tests/util_tensors.py`** — 15 lines, no deps. Unblocks everything below.
2. **`tests/reference.py`** — the NumPy attention function. Depends on nothing.
3. **`tests/test_reference_matches_torch.py`** — writes the 18 parametrized cases. Immediately validates step 2 against PyTorch. **At this point, M1 is functionally done for Python consumers.**
4. **`csrc/attention_cpu_ref.hpp`** — port the NumPy ref line-by-line into templated C++. Because NumPy is already validated in step 3, and the C++ mirrors it, the C++ is correct by construction.

Not mandatory to do it in this order — but this ordering means every step has a *test* attached, so you never write more than ~50 lines without seeing green.

## 13. Understanding checkpoint (answer these out loud)

Before ticking M1 done, you should be able to answer these without notes:

1. **Softmax stability.** *What happens if you skip the `-max` shift?*
   Concrete answer with `x = [100, 100, 100]`: naive gives `inf/inf = NaN`; shifted gives `[1/3, 1/3, 1/3]`.

2. **Choice of oracle.** *Why compare to `torch.nn.functional.scaled_dot_product_attention` instead of re-writing `Q@K.T` in NumPy again?*
   Two reasons: (a) stronger cross-check — PyTorch is an *independent* implementation, so agreeing to 1e-5 is meaningful; (b) it's the user contract — our kernel will eventually replace this function.

3. **The correctness chain.** *If you had a transposition bug in `K` (used `K` instead of `K.T`), which link in the chain catches it?*
   The NumPy-vs-PyTorch test. Because PyTorch does the transpose correctly and our NumPy would not.

4. **The scale factor.** *What goes wrong if you forget to divide by `√D`?*
   For large `D`, pre-softmax scores blow up in magnitude, softmax saturates (near one-hot), gradients vanish. Also: your test tolerance will silently pass on tiny `N=8`, `D=8` cases and fail on realistic shapes later.

5. **Causal + stability.** *Why doesn't the causal mask break the softmax stability trick?*
   `-inf` entries are ignored by `max`; `-inf - m = -inf`; `exp(-inf) = 0`. The two tricks compose cleanly.

## 14. Glossary

| Term | Meaning |
|---|---|
| **Attention** | The `O = softmax(QK^T / √D) V` operation. |
| **Q, K, V** | Query, key, value tensors. Shape `[B, H, N, D]`. |
| **B / H / N / D** | Batch / heads / sequence length / head dim. |
| **S** | Pre-softmax scores. `S = QK^T / √D`. Shape `[N, N]` per `(b, h)`. |
| **P** | Post-softmax attention probabilities. Rows sum to 1. Shape `[N, N]`. |
| **O** | Output. `O = P V`. Shape `[N, D]` per `(b, h)`. |
| **SDPA** | Scaled dot-product attention. `torch.nn.functional.scaled_dot_product_attention`. |
| **Softmax stability trick** | Subtracting the row max before exponentiating, to prevent overflow. |
| **Causal mask** | Setting `S[i, j] = -inf` for `j > i`, so query `i` can't see future tokens. |
| **Oracle** | A known-correct implementation used to check other implementations. In M1, our NumPy ref *is* the oracle. |
| **Tautology test** | A test where both sides secretly use the same implementation — passes even when both are wrong. |
| **Coalesced access** | GPU memory access pattern where threads in a warp hit consecutive addresses. ~10× faster. Relevant M4+, not M1. |
| **Row-major** | Memory layout where the last dim varies fastest. Our layout for `[B, H, N, D]`. |
| **fp32 / fp64 / float32 / float64** | 32-bit / 64-bit floating point. fp64 = "double precision." |
